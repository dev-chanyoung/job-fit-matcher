# job-judge — 채용공고 지원적합도 분석 도구

이 디렉토리에서 작업할 때 아래 내용을 표준 절차로 따른다. 블루프린트 원본:
`../docs/채용공고_분석시스템_개발청사진.md`.

## 기본 실행 방식: Claude Code 세션 직접 판별 (무료)

`ANTHROPIC_API_KEY`는 기본적으로 비어 있다 (Claude Code Pro/Max 구독과 별개의 유료 API이므로 사용
안 함). 사용자가 채용공고 URL이나 JD 텍스트를 붙여넣으면, Claude Code 세션(나)이 직접 정규화·평가를
수행하고 `judge_manual.py`로 하드필터/Notion 저장만 코드에 맡긴다. `judge.py`(완전 자동화, API 키
필요)는 사용자가 나중에 API 크레딧을 결제하면 쓸 수 있도록 남겨둔 대체 경로일 뿐, 기본 경로가 아니다.

### 처리 흐름 (매번 이 순서로)

1. **입력 받기**: URL이면 WebFetch로 본문 확인, 텍스트면 그대로 사용.
2. **정규화**: `schemas.py`의 `JobPosting` 필드에 맞춰 JSON으로 직접 작성 (회사/직무/필수요건/
   우대사항/기술스택/마감일 등). 본문에 없는 정보는 추측하지 말고 `missing_fields`에 기록.
3. **하드필터 먼저 실행** (LLM 사용 금지 구간 — `hard_filter.py`가 이미 코드로 처리):
   ```
   python judge_manual.py <job.json>
   ```
   - 탈락(`required_years`에 "3년" 포함 / `deadline` 지남 / `education_requirement`에 "졸업자"
     포함하되 "졸업예정" 미포함)이면 자동으로 Notion 저장 후 종료. **평가 단계로 넘어가지 않는다
     — 토큰 낭비 방지.**
   - 통과 시 "PASSED" 메시지만 뜨고 저장 안 됨 → 다음 단계로.
4. **평가** (통과한 경우만): `profile.md`와 대조해서 `Evaluation` JSON 직접 작성.
   - **판정 기준**: "합격 확률"은 절대 계산하지 않는다 (경쟁률/내부 기준을 알 수 없어 근거 없는
     추측이 됨). 대신 "서류 경쟁력"만 평가.
   - **배점** (scores, 총 100점): 필수요건_충족(0-30) / 기술스택_일치(0-25) / 업무내용_일치(0-20) /
     우대사항(0-15) / 도메인_연관성(0-10).
   - **근거 없으면 0점** 처리. 유사 경험을 동일 경험으로 취급하지 않는다 (match_level="일부"로
     구분). evidence는 JD 요구사항 1개당 최소 1개 작성 — **이 evidence 항목들이 Notion 결과분석의
     "적합한 부분"/"부족한 부분" 문장을 만드는 재료이므로, 점수만 매기지 말고 jd_requirement/
     profile_basis를 구체적으로 채운다.**
   - **verdict**: "적극 지원" / "지원 고려" / "보류" 중 하나.
   - scores(배점)는 계속 계산하지만, Notion에는 **참고용 보조 정보로만** 들어간다 (아래 참고).
5. **저장**:
   ```
   python judge_manual.py <job.json> --evaluation <evaluation.json>
   ```
   Notion 저장은 항상 코드(`notion_writer.py`)가 담당 — LLM이 직접 Notion에 값을 쓰지 않는다
   (필드 쓰기 권한 규칙은 아래 참조).

### Notion 필드 쓰기 권한 (절대 규칙 — notion_writer.py가 이미 강제함)

| 그룹 | 필드 | 규칙 |
|---|---|---|
| 자동 채움 | 회사명/직무명/공고링크/마감일/기술스택(고정 옵션만)/연차요건 | 항상 자동 작성 |
| 제안 | 결과분석 | Evaluation 요약 텍스트로 작성 (사람이 검토) |
| **자동화 금지** | **지원상태/우선순위/지원동기메모** | **절대 코드로 건드리지 않음** (신규/기존 행 모두) |

기업규모/도메인은 확신 없으면 컬럼에 값을 넣지 않고 결과분석 텍스트에 "추정: OO"로만 남긴다.

### 결과분석 형식: 점수보다 정성적 판단 우선

사용자가 "점수만 보고는 판단하기 어렵다"고 명확히 요청해서, `format_result_analysis()`는 점수를
헤드라인으로 쓰지 않는다. 순서는 항상: **판정 → 적합한 부분(강함/일부 매치 evidence) → 부족하거나
안 맞는 부분(미확인/없음 매치 evidence + gaps) → 자소서 소재 → (참고) 배점**. 이 구조를 코드에서
건드릴 때 점수를 다시 맨 위로 올리지 않는다 — evidence의 jd_requirement/profile_basis/match_level
필드가 그대로 "왜 맞는지/왜 안 맞는지" 문장이 되므로, Evaluation JSON 작성 시 이 필드들을 구체적으로
채우는 게 배점 자체보다 중요하다.

## profile.md 관리 정책 (토큰 절약 핵심)

`profile.md`는 매 평가마다 프롬프트에 통째로 들어가는 **캐시된 단일 진실 소스**다.

- **GitHub 저장소 링크가 있어도 자동으로 매번 들어가서 확인하지 않는다.** 저장소 분석은 무거운
  작업이라 평가할 때마다 반복하면 토큰 낭비.
- 사용자가 저장소 분석을 요청하면 (또는 profile.md에 아직 요약되지 않은 새 링크를 발견하면):
  1. 그 저장소를 **한 번만** 확인 (README, 주요 구조, 커밋/PR 요약 등 — 필요한 부분만, 저장소
     전체를 긁지 않는다).
  2. 프로젝트명/역할/문제/해결방법/성과(수치)/근거 형태로 정리.
  3. **profile.md의 "프로젝트별 경험" 섹션에 직접 써서 영구 반영**한다 (링크만 남겨두지 않는다).
  4. 이후 평가는 이 정리된 텍스트만 읽는다 — 저장소를 다시 열지 않는다.
- profile.md는 장황한 문장보다 **정보 밀도 높은 불릿**으로 유지 (프롬프트 토큰 비례).
- profile.md의 모든 항목(프로젝트/수상/봉사/자격증 등)은 끝에 `- 키워드: ` 태그를 단다 (예:
  `성능최적화`, `협업`, `봉사`). 자소서 문항이 왔을 때 이 파일에서 키워드로 검색해 바로 어떤 경험을
  쓸지 찾기 위함 — 새 항목을 추가/정리할 때 이 태그를 빠뜨리지 않는다.

## 환경 설정 관련 주의사항

- `.env`에는 실제 키, `.env.example`에는 **절대 실제 값을 넣지 않는다** (git에 커밋되는 템플릿
  파일이라 유출 위험). `.gitignore`에 `.env`가 이미 등록되어 있다.
- `NOTION_DB_ID`는 Notion URL에서 `?v=...` 뒷부분을 뺀 32자리 ID만 사용한다.
- Notion API는 2025-09+ 기준 "데이터소스" 구조로 바뀌었다: `client.databases.query`는 더 이상
  존재하지 않고 `client.data_sources.query(data_source_id=...)`를 쓴다. `notion_writer.py`의
  `_resolve_data_source_id()`가 이미 이 변환을 처리하므로, 이 프로젝트 코드를 건드릴 때 옛날 API
  방식(`databases.query`, `parent={"database_id": ...}`)으로 되돌리지 않는다.
- Windows 콘솔은 기본 cp949라서 `judge.py`/`judge_manual.py`는 시작 시 stdout/stderr를 UTF-8로
  강제 재설정한다. 새 CLI 진입점을 추가할 때도 이 패턴을 따른다 (em dash 등 특수문자가 아니어도
  깨질 수 있음).
- 코드를 고칠 때는 **mock 테스트 통과만으로 끝났다고 하지 말고**, 최소 한 번은 실제
  `python judge_manual.py <file>` 같은 실행으로 콘솔 출력까지 확인한다 (CliRunner 캡처와 실제
  콘솔 인코딩 동작이 다를 수 있음 — 실제로 이 프로젝트에서 그렇게 버그를 하나 놓쳤었다).

## Git 정책

이 프로젝트는 사용자가 **자동 commit+push를 명시적으로 승인**했다 (2026-09-16). 코드/설정/
profile.md가 바뀌면, 매번 확인받지 않고 의미 있는 단위로 커밋 후 `git push`까지 수행한다
(데스크탑/노트북 간 동기화가 이 저장소의 존재 목적이므로). 원격 저장소:
`https://github.com/dev-chanyoung/job-fit-matcher` (private). `.env`는 계속 gitignore 대상 —
자동 push라도 `.env`를 커밋 대상에 포함하지 않는다.
