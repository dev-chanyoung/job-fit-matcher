# job-judge — 채용공고 지원적합도 분석 도구

이 디렉토리에서 작업할 때 아래 내용을 표준 절차로 따른다. 블루프린트 원본:
`../docs/채용공고_분석시스템_개발청사진.md`.

## 기본 실행 방식: Claude Code 세션 직접 판별 (무료)

`ANTHROPIC_API_KEY`는 기본적으로 비어 있다 (Claude Code Pro/Max 구독과 별개의 유료 API이므로 사용
안 함). 사용자가 채용공고 URL이나 JD 텍스트를 붙여넣으면, Claude Code 세션(나)이 직접 정규화·평가를
수행하고 `judge_manual.py`로 하드필터/Notion 저장만 코드에 맡긴다. `judge.py`(완전 자동화, API 키
필요)는 사용자가 나중에 API 크레딧을 결제하면 쓸 수 있도록 남겨둔 대체 경로일 뿐, 기본 경로가 아니다.

### 처리 흐름 (매번 이 순서로)

1. **입력 받기**: URL이면 WebFetch로 본문 확인, 텍스트면 그대로 사용.
   - **WebFetch로 본문이 안 나오면 브라우저로 직접 연다 (2026-10-03 사용자 지시)**: 제목·마감일 같은
     뼈대만 나오거나 "공고 내용을 찾을 수 없다"는 응답이 오면, 서버가 본문을 자바스크립트로 나중에
     내려주거나(예: `*.recruiter.co.kr` 계열은 본문 API가 접근 거부 400을 돌려줘서 코드로 못 가져옴),
     본문이 통째로 이미지인 공고다. 이때는 추측하거나 사용자에게 붙여넣어 달라고 하기 전에 아래를
     먼저 한다.
     ```
     python fetch_rendered.py <url> --download-dir <임시폴더> --slice
     ```
     `fetch_rendered.py`가 PC의 Edge/Chrome을 헤드리스로 띄워 자바스크립트가 실행된 뒤의 화면 텍스트와
     이미지 URL을 출력하고, 본문 이미지를 내려받아 폭 1000px·1500px 높이로 잘라 `slices/`에 둔다.
     **이미지 안의 글자는 코드가 읽지 않는다** -- 세션이 잘라 둔 조각을 Read 도구로 열어서 읽는다(통째로
     열면 축소돼 글자가 뭉개진다). 이렇게 읽은 내용으로 `JobPosting`을 채운다. 브라우저 연동 도구
     (Claude in Chrome 등)가 세션에 있으면 그쪽을 써도 되지만, 없어도 이 스크립트로 같은 결과를 얻는다.
   - 사람인 `relay/view`처럼 iframe 안에 본문이 있는 경우는 아래 1차 분류 절의 `view-detail` 방식이
     먼저다(브라우저 없이 WebFetch만으로 됨).
   - 사람인·자소설닷컴 같은 수집본에는 우대사항·기술스택이 빠져 있을 수 있다. 같은 공고의 회사 채용
     페이지 원문을 이 방식으로 열어 보면 사람인 요약에 "없음"이던 우대사항이 나오는 경우가 있다(실제로
     원문 확인 뒤 점수가 3~7점 내려간 공고가 있었다). 요약에서 "없음(만점 처리)"로 둔 공고를 지원 대상으로
     정했다면 원문을 한 번 열어 본다.
2. **정규화**: `schemas.py`의 `JobPosting` 필드에 맞춰 JSON으로 직접 작성 (회사/직무/필수요건/
   우대사항/기술스택/마감일 등). 본문에 없는 정보는 추측하지 말고 `missing_fields`에 기록.
   `company_size`/`domain`도 이 단계에서 직접 판단해서 채운다 (아래 Notion 필드 쓰기 권한 표 참조) —
   기업이 잘 알려져 있으면(계열사 여부, 사업 영역 등으로) 추측이 아니라 판단이므로 적극적으로 채운다.
3. **하드필터 먼저 실행** (LLM 사용 금지 구간 — `hard_filter.py`가 이미 코드로 처리):
   ```
   python judge_manual.py <job.json>
   ```
   - 탈락 사유는 두 가지뿐이다: (1) `hard_filter.extract_mandatory_min_years()`가 판단한 경력
     요건 미충족 — 신입 대체경로("신입 또는 경력 3년 이상" → 통과, 단 "신입 지원 불가"처럼 근처에
     부정어가 있으면 대체경로로 안 침), 우대 여부(콤마/슬래시로 나뉜 절 안에 "우대"가 있을 때만 그
     절의 연차 요건을 통과 처리 — "경력 3년 이상, 금융권 경험 우대"는 뒤 절의 우대가 앞 절 3년
     요건까지 봐주지 않는다), 최소 연차 0년(사실상 무관)은 애초에 탈락 사유로 안 침. "경력 5년 이상
     필수"처럼 명확한 경우만 탈락시키고, 해석이 애매한 문구는 자동 탈락시키지 않는다. (2) `deadline`
     지남. 탈락하면 자동으로 Notion 저장 후 종료. **평가 단계로 넘어가지 않는다 — 토큰 낭비 방지.**
     (`education_requirement`의 "졸업자만 지원 가능" 문구는 탈락 사유로 취급하지 않는다 — 지원자는
     2026년 8월에 이미 졸업했으므로 이 요건은 애초에 걸릴 일이 없다. 2026-09-19 사용자 확인.)
   - 통과 시 "PASSED" 메시지만 뜨고 저장 안 됨 → 다음 단계로.
4. **평가** (통과한 경우만): `profile.md`와 대조해서 `Evaluation` JSON 직접 작성.
   - **판정 기준**: "합격 확률"은 절대 계산하지 않는다 (경쟁률/내부 기준을 알 수 없어 근거 없는
     추측이 됨). 대신 "서류 경쟁력"만 평가.
   - **배점** (scores, 총 100점): 필수요건_충족(0-30) / 기술스택_일치(0-25) / 업무내용_일치(0-20) /
     우대사항(0-15) / 도메인_연관성(0-10).
   - **근거 없으면 0점** 처리. 유사 경험을 동일 경험으로 취급하지 않는다 (match_level="일부"로
     구분). evidence는 JD 요구사항 1개당 최소 1개 작성 — **이 evidence 항목들이 Notion 결과분석의
     "적합한 부분"/"부족한 부분" 문장을 만드는 재료이므로, 점수만 매기지 말고 jd_requirement/
     profile_basis를 구체적으로 채운다.**
   - **배점 대비 % 기준** (2026-09-19 고정값으로 확정 — 범위를 쓰면 같은 근거에도 사람마다/회차마다
     다른 숫자를 골라 재현이 안 됨): 항목 점수는 21점/23점처럼 임의의 숫자를 고르지 않고, 아래 5개
     고정값 중 하나를 고른 뒤 왜 그 단계인지 profile_basis에 한 문장 근거를 남긴다.

     | 근거 수준 | 배점 대비 | 인정 기준 |
     |---|---:|---|
     | 직접 충족 | 100% | JD가 요구하는 수준을 본인이 직접 수행·설명한 근거가 있음 |
     | 범위 일부 부족 | 75% | 같은 일을 했지만 요구된 범위·복잡도·책임의 일부가 빠짐 |
     | 유사 경험(전이 가능) | 50% | 다른 기술·환경에서 비슷한 문제를 해결했고 전이 가능한 부분과 차이를 설명 가능 |
     | 기초 수준만 확인 | 25% | 실무 요구 수준엔 못 미치지만 수업·기초실습 등 관련 경험만 확인 |
     | 확인된 미충족 / 정보 없음 | 0% | `match_level="없음"`(확인된 미충족)과 `match_level="미확인"`(정보 없음)을 반드시 구분 |

     `match_level="일부"`는 "범위 일부 부족"과 "유사 경험" 두 경우를 모두 포함하므로, 어느 쪽인지
     profile_basis에 명시한다.
   - **카테고리 내 여러 요구사항 합산 + 계산 근거 기록** (2026-09-19): 한 항목(예: 기술스택_일치)에
     요구사항이 여러 개 걸리면 각각 %를 먼저 정한 뒤 가중평균해서 배점에 곱한다. JD 원문에
     "핵심"/"주요"/"필수"라고 명시된 요구사항만 가중치 2배로 평균에 반영한다 — 순서가 앞이거나 여러
     번 등장한다는 이유만으로 가중치를 올리지 않는다. 요구사항이 2개 이상인 카테고리는 이 계산을
     `Evaluation.score_breakdown[카테고리명]`에 한 줄로 남긴다 (요구사항이 1개뿐이라 계산이랄 게
     없으면 생략 가능). 형식 예:
     ```
     Java 100%x2, Spring 75%x2, Redis 25%x1 -> (100x2+75x2+25x1)/5=75% -> 25x0.75=18.75/25 -> 19점
     ```
   - **반올림은 마지막에 한 번만**: 카테고리 % 가중평균은 소수 그대로 유지하고, "% x 배점"을 계산한
     최종값에서만 반올림해서 `scores`에 넣는 정수를 만든다. 중간 단계(항목별 %, 가중합)를 각각
     반올림한 뒤 더하면 최종 정수가 미묘하게 달라질 수 있으므로 하지 않는다.
   - **카테고리 간 중복 채점 금지**: 같은 사실(예: "Java 사용 경험")을 여러 항목에서 반복 채점하지
     않는다. 항목마다 다른 속성만 본다 — 기술스택_일치는 "그 기술을 아는지/써봤는지", 업무내용_일치는
     "그 기술로 실제 어떤 업무를 했는지", 필수요건_충족은 "위 둘 중 JD가 필수로 못박은 것을
     충족했는지"만 확인한다. 하나의 근거를 세 항목에서 각각 가점하지 않는다.
   - **조건 없음(N/A) vs 확인 못함 구분**: JD 원문에 해당 항목 조건이 아예 없다고 확인되면(예:
     우대사항 섹션 자체가 없음) 그 항목은 만점 처리하고 결과분석에 "OO: 명시된 요건 없음(만점 처리)"라고
     남긴다. 있는지 없는지 판단이 안 되면 0점을 주되 evidence_quality를 "자료 부족"으로 표시하고
     결과분석에 "확인 필요"라고 남긴다 — 없다고 단정하지 않는다.
   - **우대사항 중 직무 무관 항목은 없는 셈 치고 채점** (2026-09-20 사용자 확인): 국가유공자·장애인·
     보훈(취업지원)대상자, 특정 자격 보유 시 시험 면제(예: 변호사·공인회계사의 전공필기 면제)처럼
     지원자의 직무 역량과 무관한 법정/신분 요건은 우대사항 항목 목록에서 아예 빼고 채점한다 —
     "없음(0%)"으로 감점하지 않는다. 이런 항목만 있고 직무 관련 우대사항이 하나도 없다면
     우대사항 카테고리 자체가 "명시된 요건 없음"인 것으로 보고 위 N/A 규칙대로 만점 처리한다.
     직무와 조금이라도 관련된 우대사항(자격증, 기술, 관련 경험 등)은 이 예외에 해당하지 않고
     그대로 채점한다.
   - **summary(총평)**: 2~4문장으로 판정 이유를 압축 요약한다 — evidence/gaps/risks를 다시 줄줄이
     나열하지 않고, "왜 이 판정인지"를 새로 읽는 사람이 한 번에 파악하도록 쓴다(2026-09-23 사용자
     요청). `format_result_analysis()`가 이 텍스트를 "(참고) 배점:" 바로 위에 "총평: "으로 자동
     삽입하므로, Evaluation JSON 작성 시 이 필드를 빠뜨리지 않는다(하드필터 탈락처럼 Evaluation
     자체가 없는 경우는 해당 없음).
   - **verdict**: "적극 지원" / "지원 고려" / "보류" 중 하나. 총점 임계값으로 코드가 대신 정하지
     않는다 (정성 판단 우선 정책 유지) — 단, `필수요건_충족`이 배점(30) 대비 1/3 미만인데 verdict가
     "적극 지원"이면 `notion_writer.format_result_analysis()`가 **코드로** "⚠ 점수-판정 불일치"
     경고를 자동으로 붙인다 (2026-09-19: 처음엔 LLM이 챙겨야 하는 지침으로만 적어뒀는데 실제로는
     안 지켜져도 표시가 안 됐음 — 이제 코드가 검사하므로 Evaluation 작성 시 이 문구를 직접 쓸
     필요는 없다). 판정 자체는 코드가 덮어쓰지 않는다.
   - scores(배점)는 계속 계산하지만, Notion에는 **참고용 보조 정보로만** 들어간다 (아래 참고).
5. **저장 전 중복 확인 (2026-09-23 사용자 요청)**: `notion_writer._find_existing_page_id()`의 자동
   중복 감지는 공고링크(URL)+직무명 정확히 일치할 때만 잡는다 — 같은 그룹 공채가 job-watcher에 다른
   URL로 다시 잡히거나 회사명 표기가 살짝 다르면(예: "A사" vs "A사(커머스부문)") 자동 감지를
   피해서 중복 행이 생길 수 있다(실제로 2026-09-23에 A사 커머스부문 백엔드개발이 이렇게 중복
   생성된 적 있음). `judge_manual.py`를 실행하기 전에 Notion을 조회해서 **같은 회사/계열사/부문 +
   직무**가 이미 있는지 먼저 확인한다 — URL만 보고 "새 공고"라고 단정하지 않는다. 이미 있으면 새 행을
   만들지 말고 기존 행을 최신 평가로 업데이트(또는 최신 버전만 남기고 구버전 정리)한다.
   ```
   python judge_manual.py <job.json> --evaluation <evaluation.json>
   ```
   Notion 저장은 항상 코드(`notion_writer.py`)가 담당 — LLM이 직접 Notion에 값을 쓰지 않는다
   (필드 쓰기 권한 규칙은 아래 참조).
6. **본문 블록 작성 (신규 행마다 필수, 생략 금지)**: `notion_writer.save()`는 프로퍼티만 만들고
   페이지 본문(blocks)은 전혀 건드리지 않는다. `결과분석` 프로퍼티가 이제 판정 한 줄 요약뿐이라
   (위 표 참고), 새로 만든 행은 본문에 상세 분석을 직접 채워 넣지 않으면 그 공고에 대한 상세 근거가
   표에도 본문에도 없이 완전히 사라진다 — `client.blocks.children.append(block_id=새페이지id,
   children=[...])`로 직접 쌓는다(새 페이지라 기존 내용이 없으므로 삭제·재생성 필요 없음). 표준
   블록 순서: `heading_1("회사 - 직무")` → 기본정보(공고링크/마감일/지원상태, 문단 1개) →
   `heading_2("JD 원문")` + 자격요건/담당업무/우대사항 불릿 → `heading_2("🔍 회사/포지션 분석")` +
   `notion_writer.format_result_analysis_blocks(evaluation, version=..., uncertain_company_size=...,
   uncertain_domain=...)`가 돌려주는 블록 리스트를 그대로 →
   `heading_2("✍️ 자소서/이력서 포인트")` + `cover_letter_topics` 불릿. 이미 다운로드해둔 원본 공고
   이미지가 있으면 `heading_1` 바로 다음에 image 블록(파일 업로드 API, 5MB 초과 시 PIL로 압축)을
   끼워 넣는다.

| **자동화 금지** | **우선순위/지원동기메모** | **절대 코드로 건드리지 않음** (신규/기존 행 모두) |
| 사용자 작성 + 제안(append-only) | 자기소개서 문항 | 사용자가 실제 지원할 회사/직무 행에 문항 원문을 직접 붙여넣는다(코드/LLM이 채우지 않음). 세션 시작 시 SessionStart 훅(`python essay_keywords.py check --json-hook`)이 `→ 키워드 후보:` 줄이 없는 문항(pending)이 있으면 컨텍스트로 알려주고, 그 알림을 보면 profile.md와 대조해 문항별 소재를 판단한 뒤 `python essay_keywords.py apply <page_id> <suggestions.json>`으로 저장한다 — `apply`는 `notion_writer.update_essay_questions()`를 거쳐 이 프로퍼티 한 개만 쓰고, 원문은 절대 수정/삭제하지 않으며 오직 문항 블록 끝에 제안 줄을 추가(append)만 한다. |

### 상세 분석(페이지 본문) 형식: 점수보다 정성적 판단 우선

`format_result_analysis()`가 만드는 텍스트는 이제 Notion 프로퍼티가 아니라 **페이지 본문**에 들어간다
(위 "본문 블록 작성" 참고 — 결과분석 프로퍼티는 판정 한 줄 요약뿐). 사용자가 "점수만 보고는 판단하기
어렵다"고 명확히 요청해서, 이 함수는 점수를 헤드라인으로 쓰지 않는다. 순서는 항상: **판정 → 정보 충분도(evidence_quality) → 적합한 부분(강함/일부
매치 evidence) → 부족하거나 안 맞는 부분(미확인/없음 매치 evidence + gaps) → 위험 요인(risks, 있을
때만) → 자소서 소재 → 총평(evaluation.summary, 있을 때만) → (참고) 배점(+ score_breakdown 계산
근거, 있을 때만)**. 총평은 위 항목들을 요약하는 한 문단이지 새 판단을 추가하는 자리가 아니다 — 이 구조를 코드에서
건드릴 때 점수를 다시 맨 위로 올리지 않는다 — evidence의 jd_requirement/profile_basis/match_level
필드가 그대로 "왜 맞는지/왜 안 맞는지" 문장이 되므로, Evaluation JSON 작성 시 이 필드들을 구체적으로
채우는 게 배점 자체보다 중요하다.

**본문에는 텍스트가 아니라 `format_result_analysis_blocks()`의 블록을 쓴다** (2026-10-03 사용자 요청:
위 텍스트를 문단 하나에 통째로 넣었더니 가독성이 너무 나쁘다며 이모지·줄바꿈·노션 기능으로 정리해달라고
함). 내용은 위 텍스트와 같고 배치만 다르다: 판정 콜아웃(판정·정보 충분도·총점, 판정별 이모지/색) →
점수-판정 불일치 경고 콜아웃(있을 때) → 💬 총평 콜아웃(맨 아래가 아니라 판정 바로 밑으로 올림) → 범례
→ ✅ 적합한 부분 / ⚠️ 부족하거나 안 맞는 부분(heading_3) → 🚩 위험 요인 → 📊 배점 상세 토글(계산식은
접어둠). evidence 항목은 **글머리표가 아니라 문단 블록**으로 만들고 맨 앞의 🟢/🟡/⚪/🔴(강함/일부/미확인/
없음) 이모지가 글머리표 역할을 한다 — 글머리표로 만들면 검은 점과 색 점이 나란히 보여서 사용자가 빼달라고
요청함. JD 요건은 굵게, 근거는 줄을 바꿔 "→ …"로 쓴다. 자소서 소재는 본문의 "✍️ 자소서/이력서 포인트"
섹션과 겹치므로 기본으로 넣지 않는다. 텍스트 버전(`format_result_analysis()`)은 테스트와 다른 용도를 위해
남겨둔다.

## profile.md 관리 정책 (토큰 절약 핵심)

`profile.md`는 매 평가마다 프롬프트에 통째로 들어가는 **캐시된 단일 진실 소스**다.

- **개인정보라 git에 올리지 않는다** (2026-09-26, 저장소 공개 전환에 맞춰 결정). `job-judge/.gitignore`에
  등록돼 있어 각 PC에 로컬 파일로만 존재한다. 새 환경에서는 `profile.example.md`를 `profile.md`로 복사해
  채우고, PC 간 동기화는 사용자가 직접 한다. 자동 commit+push 대상이 아니다.

- **GitHub 저장소 링크가 있어도 자동으로 매번 들어가서 확인하지 않는다.** 저장소 분석은 무거운
  작업이라 평가할 때마다 반복하면 토큰 낭비.
- 사용자가 저장소 분석을 요청하면 (또는 profile.md에 아직 요약되지 않은 새 링크를 발견하면):
  1. 그 저장소를 **한 번만** 확인 (README, 주요 구조, 커밋/PR 요약 등 — 필요한 부분만, 저장소
     전체를 긁지 않는다).
  2. 프로젝트명/역할/문제/해결방법/성과(수치)/근거 형태로 정리.
  3. **profile.md의 "프로젝트별 경험" 섹션에 직접 써서 영구 반영**한다 (링크만 남겨두지 않는다).
  4. 이후 평가는 이 정리된 텍스트만 읽는다 — 저장소를 다시 열지 않는다.
- profile.md는 장황한 문장보다 **정보 밀도 높은 불릿**으로 유지 (프롬프트 토큰 비례).
- profile.md의 모든 항목(프로젝트/수상/봉사/자격증 등)은 끝에 `- 키워드: ` 태그를 단다 (예:
  `성능최적화`, `협업`, `봉사`). 자소서 문항이 왔을 때 이 파일에서 키워드로 검색해 바로 어떤 경험을
  쓸지 찾기 위함 — 새 항목을 추가/정리할 때 이 태그를 빠뜨리지 않는다.

## 자기소개서 문항 키워드 제안 워크플로 (2026-09-17 사용자 요청)

지원할 마음이 생긴 공고의 자소서 문항을 미리 Notion에 적어두면, 나중에 초안 쓸 때 어떤 경험을
써야 할지 바로 알 수 있게 하는 기능. 문항 원문과 키워드 제안을 **한 속성(자기소개서 문항)에 같이**
넣는다 — 두 속성으로 분리하지 않는다 (사용자가 "보기 편함"을 이유로 명시적으로 선택).

- **사용자가 하는 일**: 지원할 회사/직무의 Notion 행에서 "자기소개서 문항" 칸에 문항 원문을 그대로
  붙여넣기만 하면 된다. 문항이 여러 개면 빈 줄로 구분.
- **세션 시작 시 자동 감지**: SessionStart 훅이 `python essay_keywords.py check --json-hook`을
  실행해 `→ 키워드 후보:` 줄이 아직 없는 문항(pending)이 있으면 세션 컨텍스트로 알려준다. 코드는
  "문항이 채워졌는데 제안이 없다"는 사실만 감지할 뿐, 소재를 판단하지 않는다 — 그건 LLM(나)의 몫.
- **알림을 받으면 이렇게 처리**: profile.md와 대조해서 문항마다 어떤 프로젝트/경험이 적합한지
  판단하고, `{"문항 원문": "키워드 후보 텍스트"}` 형태의 JSON을 만들어
  `python essay_keywords.py apply <page_id> <suggestions.json>`으로 저장한다.
- **append-only 보장**: `apply`는 `notion_writer.update_essay_questions()`를 통해 "자기소개서
  문항" 프로퍼티 하나만 쓰고, 이미 `→ 키워드 후보:`가 붙은 문항은 건드리지 않는다(`notion_writer.
  find_pending_questions`/`apply_keyword_suggestions`). 사용자가 원문을 지우거나 고치지 않는 한
  절대 원문을 수정하지 않는다.
- 이 워크플로는 `judge_manual.py`의 하드필터/평가 파이프라인과 완전히 독립적이다 — job.json이나
  Evaluation JSON을 거치지 않고, 기존에 저장된 Notion 행을 대상으로만 동작한다.

## 세션 시작 시 자동 1차 분류 워크플로 (2026-09-22 사용자 요청)

`job-watcher`(`../job-watcher`)는 신규 공고를 발견하면 Discord에 그대로(필터링 없이) 알림만 보낸다.
매번 그 목록 전체를 훑어보기엔 부담스럽다는 사용자 요청으로, Claude Code 세션이 시작될 때마다 그동안
쌓인 신규 공고를 가볍게 훑어서 **적합/애매/부적합** 세 등급으로 나눠 Discord에 다시 정리해서 보내는
기능이다. 이건 `judge_manual.py`가 하는 정식 4단계 정성평가(근거별 배점, Notion 저장)가 **아니다** —
그 무거운 평가를 할 가치가 있는 공고만 먼저 걸러내는 가벼운 사전 필터다. 3단계로 정한 이유: 이 단계는
근거 하나하나를 대조하는 정밀 판단이 아니라 "정성평가할 가치가 있는지"만 보는 거라, "적합"과
"어느정도 맞음" 같은 세밀한 경계를 두면 실행마다 기준이 흔들려 재현성이 떨어진다 — 세 갈래(볼 것 /
애매해서 훑어볼 것 / 패스)면 충분하고 Discord embed 공간도 덜 든다.

- **역할 분담**: `mongo_reader.py`/`discord_poster.py`/`batch_classify.py`는 기계적인 부분만
  처리한다 — 후보 목록 조회(MongoDB), 분류 상태 기록(MongoDB), Discord 전송. **등급을 매기는 판단
  자체는 항상 Claude Code 세션(나)의 몫**이지 코드가 하지 않는다 (하드필터/평가 단계의 역할 분담과
  동일한 원칙).
- **후보 소스**: `job-watcher`가 `job_watcher.seen_postings`(MongoDB, URL이 `_id`)에 신규 공고를
  적어둔다. `job-judge`는 여기서 **읽기만** 하고, 같은 DB의 `job_judge_classified` 컬렉션에 자기
  상태만 쓴다 — `job-watcher`의 컬렉션은 절대 건드리지 않는다.
- **SessionStart 훅**: `python batch_classify.py candidates --json-hook`이 `seen_postings`에는
  있지만 `job_judge_classified`에는 없는(=아직 1차 분류 안 된) 공고가 있으면 세션 컨텍스트로 알려준다
  (`.claude/settings.json`, essay_keywords.py 훅과 같은 패턴). `MONGODB_URI`가 로컬에 아직 없거나
  DB 연결이 안 되면 세션 시작을 막지 않도록 조용히 넘어간다(에러 없음) — 이 기능은 선택 사항이라서다.
- **알림을 받으면 이렇게 처리** (공고마다):
  1. WebFetch로 JD 확인 → 하드필터에 필요한 최소한(`required_years`/`deadline`, 그리고 등급 판단에
     쓸 `tech_stack`/`domain`/`responsibilities`)만 채운 `JobPosting`을 만든다. 정식 평가 때처럼
     모든 필드를 채울 필요는 없다 — 이 단계 목적은 등급 판단이지 저장이 아니다.
     **사람인(`saramin.co.kr`) URL 주의**: `.../jobs/relay/view?rec_idx=...` 형태 URL을 그대로
     WebFetch하면 nav/footer 뼈대만 나오고 실제 JD 본문이 안 잡힌다(2026-09-22 확인) — 본문은 같은
     origin의 `.../jobs/relay/view-detail?rec_idx=...&rec_seq=0` iframe 안에 있다. 이 URL로
     바꿔서 WebFetch하면 바로 본문이 나온다. 일부 공고(전체의 약 1/5)는 이 URL로도 자격요건 서술문
     없이 직종/기술스택 태그 요약만 나오는데, 이 경우 태그만 보고 추측하지 말고 tier="애매" +
     "자격요건 서술 없음, 태그만 확인" 같은 사유를 남긴다("확인 안 되면 추측하지 않는다" 원칙 재사용).
  2. `hard_filter.hard_filter(job)`을 그대로 재사용한다. **탈락하면 별도 LLM 판단 없이 바로
     tier="부적합"**, reason은 하드필터가 반환한 사유 문자열을 그대로 쓴다 (토큰 낭비 방지 — 정식
     평가 흐름과 동일한 원칙).
  3. **채용이 아니라 양성과정/교육과정/부트캠프면 하드필터 통과 여부와 무관하게 tier="부적합"**
     (2026-09-22 사용자 요청) — 예: "OO 양성과정", "채용연계형 교육", "부트캠프", "아카데미" 등
     정규 고용관계가 아니라 교육 이수 자체가 목적인 프로그램. reason에 "채용이 아닌 양성과정/교육
     프로그램"이라고 남긴다. "채용연계형 인턴"처럼 교육을 거쳐 실제 정규직/인턴 채용으로 이어지는
     경우는 이 규칙 대상이 아니다(채용 자체가 목적) — 채용연계 여부가 불분명하면 tier="애매"로
     넘기고 사유에 왜 애매한지 남긴다.
  4. **연구직(R&D/연구원 등)도 하드필터 통과 여부와 무관하게 tier="부적합"** (2026-09-22 사용자
     요청: "여긴 대부분 석사 이상"이라 학사 신입인 지원자 프로필과 애초에 안 맞음). 직무명/JD에
     "연구원", "Researcher", "연구개발(R&D)"처럼 연구직임이 드러나면 적용 — 개발/엔지니어 직무
     설명 중 일부 문구에 "연구"가 섞여 있다고(예: "신기술 연구·적용") 기계적으로 걸지 않는다,
     직무 자체의 성격이 연구직인지로 판단한다. reason에 "연구직 (통상 석사 이상 요건)"이라고
     남긴다.
  5. 위 세 규칙에 걸리지 않은 공고만 `profile.md`의 `- 키워드:` 태그와 JD의 기술스택/도메인/업무내용을
     가볍게 대조해서 적합/애매 중 하나로 판단하고, 왜 그런지 한 줄 reason을 남긴다 (evidence 항목별
     근거를 쓰는 정식 평가와 달리, 여기서는 한두 문장이면 충분).
- **기록 + 전송**: 세션이 처리한 후보 전체(부적합 포함)를
  `[{"url","company","title","source","tier","reason"}, ...]` JSON으로 모아
  `python batch_classify.py record <results.json>`을 **한 번만** 실행한다 — 이 명령이
  `mongo_reader.mark_classified()`로 MongoDB에 기록해서 같은 공고가 다음 세션에 다시 후보로 뜨지
  않게 하고, 동시에 `discord_poster.post_classified_results()`로 Discord 메시지를 보낸다.
  **소스 간 중복 제거 (2026-09-22 사용자 요청, 자소설닷컴 우선)**: 같은 회사가 자소설닷컴과
  사람인 양쪽에 다 뜨면(예: "G유통그룹"(자소설) / "(주)G유통"(사람인)) 같은 공고를 두 번
  추천하지 않도록, `record()`가 `batch_classify._dedupe_cross_source()`로 회사명을 느슨하게
  정규화(`(주)`/`㈜`/`주식회사`/`그룹`/공백 제거)해 비교한 뒤 우선순위가 낮은 소스(사람인)의
  항목을 Discord 전송 대상에서만 제외한다 — **MongoDB에는 원래 판정(tier/reason) 그대로 전부
  기록**하므로(제외된 항목도 `mark_classified()`는 정상 호출), 다음 세션에 같은 공고가 "아직
  미분류"로 다시 뜨는 일은 없다. 이 정규화는 휴리스틱이라 표기가 특이한 회사는 못 잡거나, 드물게
  전혀 다른 두 회사를 같은 것으로 오판할 수 있음을 감안한다 — 개인용 트래커라 사람이 Discord
  결과를 보고 최종 판단하므로 이 정도 휴리스틱이면 충분하다는 전제.
  **단, 회사명이 같아도 제목이 특정 직무를 콕 집었으면 중복 제외하지 않는다 (2026-09-23 사용자
  요청)**: 자소설닷컴은 거의 항상 그룹 전체를 묶은 통합 공고("2026 신입사원 공개채용")라 특정
  직무의 자격요건/담당업무가 안 나오는데, 같은 회사의 사람인 공고는 구체적 직무명이 붙어 있는
  경우가 많다(예: C그룹 — 자소설 "26년 하반기 신입사원 모집" vs 사람인 "…(데이터
  사이언티스트/데이터)"/"…(SAP ERP운영)"/C그룹 계열사 "…(ICT)" 등 서로 다른 계열사·직무
  공고 여러 개). 회사명만 보고 사람인 쪽을 지우면 이런 구체적 공고를 통째로 놓치므로,
  `batch_classify._is_generic_bundle_title()`로 제목에 "신입"/"경력"/"인턴" 같은 일반적인
  고용형태 괄호 외에 다른 괄호 내용(직무/부문/트랙명)이 있으면 "다른 공고"로 보고 사람인 쪽도
  그대로 Discord에 보낸다 — 정말 양쪽 다 회사 통합 공고일 때만(둘 다 특정 직무명이 없을 때만)
  기존처럼 자소설닷컴만 남긴다. 이것도 제목 문구만 보는 휴리스틱이라 괄호 밖에 직무명이 붙는
  드문 제목은 못 잡을 수 있음을 감안한다.
  **Notion에 이미 있는 회사도 동일하게 제외 (2026-09-22 사용자 요청)**: job-watcher가 같은 회사
  공고를 다른 URL/트랙으로 다시 찾아내면(예: H그룹, I항공 — 이미 여러 트랙이 Notion에 저장돼
  있음) `notion_writer.save()`의 URL+직무명 dedup으로는 못 잡으므로, `record()`가
  `_dedupe_against_notion()`으로 `notion_writer.fetch_existing_companies()`가 반환하는 Notion
  기존 회사명 전체를 같은 정규화 규칙으로 비교해서 이미 있는 회사는 Discord 전송에서 제외한다.
  이것도 MongoDB 기록에는 영향 없음(원래 tier 그대로 다 기록), Discord 전송에서만 빠진다. Notion
  조회 자체가 실패하면(키 미설정 등) 이 단계는 조용히 건너뛰고 나머지는 정상 진행한다(필수 기능이
  아님).
  **전송 순서/단위 (2026-09-22 사용자 요청)**: 임베딩을 최대 용량까지 채워서 보내지 않고, 등급
  단위로 항상 적합 → 애매 → 부적합 순서로 개별 메시지를 보낸다 — 같은 등급 안에서는 자소설닷컴/
  사람인 항목이 한 메시지 안에 서로 다른 임베드("✅ 자소설닷컴 적합 (N건)", "✅ 사람인 적합 (M건)"
  형식)로 함께 나가고, 등급이 바뀔 때만 새 메시지가 시작된다(한 등급이 너무 커서 글자수/필드수
  한도를 넘으면 그 등급 안에서만 메시지가 추가로 나뉜다). `source`는 `mongo_reader.source_from_url()`
  이 URL 도메인으로 이미 판단해서 후보 목록에 넣어주므로 그대로 쓰면 된다.
- **Notion과는 무관**: 이 워크플로는 Notion을 전혀 건드리지 않는다. "적합"으로 뜬 공고를 실제로
  지원 검토하고 싶으면, 그 URL을 다시 평소처럼 세션에 붙여넣어서 `judge_manual.py`의 정식
  하드필터+평가 흐름을 별도로 돌린다.
- **비용 특성**: 첫 활성화 시점엔 `job-watcher`가 그동안 쌓아둔 백로그 전체가 후보로 뜨므로 그 회차만
  비용이 크게 튈 수 있다 — 후보 수가 많으면(대략 15건 이상) 한 번에 다 처리하지 말고 사용자에게
  진행 여부를 먼저 물어본다. 이후 세션부터는 `job_judge_classified`가 상태를 기억하므로 매번 "그동안
  새로 들어온 것"만큼만 처리한다.

## 환경 설정 관련 주의사항

- `.env`에는 실제 키, `.env.example`에는 **절대 실제 값을 넣지 않는다** (git에 커밋되는 템플릿
  파일이라 유출 위험). `.gitignore`에 `.env`가 이미 등록되어 있다.
- `NOTION_DB_ID`는 Notion URL에서 `?v=...` 뒷부분을 뺀 32자리 ID만 사용한다.
- `MONGODB_URI`/`DISCORD_WEBHOOK_URL`(1차 분류 워크플로 전용, 둘 다 선택)은 `job-watcher`가 이미
  쓰고 있는 같은 값을 Vercel 프로젝트 설정에서 그대로 복사해서 `job-judge/.env`에 넣으면 된다 —
  job-watcher의 로컬 `.env`엔 없고(배포 환경변수로만 관리) Vercel 대시보드에만 있으므로, 필요하면
  거기서 값을 확인해야 한다.
- **일회성 스크립트에서 `load_dotenv()`를 인자 없이 호출하지 않는다** (2026-09-23 확인). 이 환경(Git
  Bash on Windows, 세션 스크래치패드처럼 job-judge 밖 경로의 파일을 `python "<긴 경로>/foo.py"`로
  실행하는 경우)에서는 인자 없는 `load_dotenv()`가 `.env`를 못 찾고 조용히 넘어가는 경우가 있고,
  이러면 `NOTION_API_KEY`가 비어서 Notion API가 **"Authorization header must use the format
  'Bearer <token>'"**라는, 마치 속도제한처럼 보이는 401을 던진다 — 실제로는 인증 헤더가 아예
  안 실렸을 뿐인데 이 오류 문구만 보고 "쓰기 속도제한에 걸렸다"고 몇 시간을 오판했던 적이 있다
  (본 프로젝트 코드 파일들은 이미 전부 `load_dotenv()`를 인자 없이 쓰고 있지만 `notion_writer.py`
  등에서는 실행 위치가 항상 `job-judge/`라 문제된 적이 없었다 — 문제는 스크래치패드 임시 스크립트를
  다른 경로에서 실행할 때만 발생). 새 임시 스크립트를 짤 때는 항상
  `load_dotenv("<job-judge 절대경로>/.env")`처럼 명시적 경로를 준다. 진짜 쓰기 속도제한(짧은 시간에
  PATCH/DELETE를 아주 많이 연달아 보냈을 때)도 존재하긴 하지만, 그 경우도 몇 초~수십 초면 회복되므로
  같은 401이 몇 분 넘게 계속되면 토큰 로딩 문제부터 의심한다.
- Notion API는 2025-09+ 기준 "데이터소스" 구조로 바뀌었다: `client.databases.query`는 더 이상
  존재하지 않고 `client.data_sources.query(data_source_id=...)`를 쓴다. `notion_writer.py`의
  `_resolve_data_source_id()`가 이미 이 변환을 처리하므로, 이 프로젝트 코드를 건드릴 때 옛날 API
  방식(`databases.query`, `parent={"database_id": ...}`)으로 되돌리지 않는다.
- Windows 콘솔은 기본 cp949라서 `judge.py`/`judge_manual.py`는 시작 시 stdout/stderr를 UTF-8로
  강제 재설정한다. 새 CLI 진입점을 추가할 때도 이 패턴을 따른다 (em dash 등 특수문자가 아니어도
  깨질 수 있음).
- 코드를 고칠 때는 **mock 테스트 통과만으로 끝났다고 하지 말고**, 최소 한 번은 실제
  `python judge_manual.py <file>` 같은 실행으로 콘솔 출력까지 확인한다 (CliRunner 캡처와 실제
  콘솔 인코딩 동작이 다를 수 있음 — 실제로 이 프로젝트에서 그렇게 버그를 하나 놓쳤었다).

## Git 정책

이 프로젝트는 사용자가 **자동 commit+push를 명시적으로 승인**했다 (2026-09-16). 코드/설정이
바뀌면, 매번 확인받지 않고 의미 있는 단위로 커밋 후 `git push`까지 수행한다. 원격 저장소:
`https://github.com/dev-chanyoung/job-fit-matcher` (**공개 저장소** — 2026-09-26 전환). 그래서
`.env`와 `profile.md`(개인정보)는 계속 gitignore 대상이고, 자동 push라도 절대 커밋하지 않는다.
공개 저장소이므로 문서·주석·테스트·커밋 메시지에 실제 지원 회사명이나 개인정보를 쓰지 않는다 —
예시가 필요하면 "A사", "B그룹"처럼 익명화한다.
