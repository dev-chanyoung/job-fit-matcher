# 개발 기록

job-fit-matcher를 어떤 순서로, 어떤 판단을 거쳐 만들었는지 정리한 문서입니다. 커밋 하나하나의 세부
내용은 커밋 메시지에, 채점 기준 개선 과정은 [평가기준 개선 전체기록](260919_평가기준_개선_전체기록.md)에
따로 있습니다.

- **기간**: 2026-09-16 ~ 진행 중
- **개발 방식**: Claude Code(AI 코딩 에이전트)와 협업. 요구사항 정의·설계 판단·검증은 사람이, 구현은
  에이전트가 맡고, 에이전트가 매번 같은 기준으로 일하도록 **하네스**(작업 규칙·훅·스키마·테스트)를 함께
  설계했습니다.
- **규모**: 커밋 40여 개 · Python 테스트 149개 · TypeScript 테스트 36개 (전부 mock 기반, API 키 없이 실행)

## 2. 1일차: 검증할 수 없는 것은 완료라고 하지 않는다

첫날은 설계 문서를 에이전트에게 넘겨 기능을 9개 단위(US-001~009)로 나눠 구현했습니다. 이때 정한 원칙이
이후 개발 전체의 기준이 됐습니다.

- **검증 범위를 먼저 정함**: 개발 환경에는 실제 API 키가 없었습니다. 그래서 "키 없이 검증 가능한 범위"
  (mock 기반 단위 테스트)까지만 완료로 보고, "실제 공고 5개를 처리해 Notion에 저장"하는 항목은 **완료라고
  하지 않고 사람이 할 후속 작업으로 명시**했습니다.
- **의존성 주입**: Anthropic·Notion·HTTP 클라이언트를 모두 주입 가능하게 만들어, 실제 서비스 없이도 전 경로를
  테스트할 수 있게 했습니다.
- **보호 필드는 한 관문으로만**: 사람이 직접 관리하는 필드(지원상태·우선순위·지원동기 메모)를 자동화가 절대
  건드리지 못하도록, Notion에 쓰는 속성은 `_build_properties()` 한 곳에서만 만들고 **보호 필드가 들어가지
  않는다는 사실을 테스트로 단언**했습니다(리뷰로 확인하는 데서 그치지 않음).
- **리뷰와 정리**: 별도 리뷰 에이전트가 소스를 직접 읽어 제어 흐름을 검증했고, 이후 두 모듈에 중복 구현된
  헬퍼를 `llm_utils.py`로 통합했습니다.

### 실제 서비스에 연결하자 드러난 문제

테스트는 모두 통과했지만, 실제 Notion 키를 연결하자 테스트로는 잡히지 않은 문제가 나왔습니다.

| 문제 | 원인 | 대응 |
|---|---|---|
| Notion 저장이 전부 실패할 상태 | 설치된 SDK가 이미 `databases.query`를 없애고 `data_sources` 구조로 바뀌어 있었음. 설계 문서는 이전 API 기준 | `_resolve_data_source_id()`로 데이터소스를 찾아 쓰도록 전환, 공식 문서로 확인 |
| DB ID 불일치 | 페이지 URL을 복사하며 뷰 ID(`?v=...`)까지 붙음 | 32자리 ID만 쓰도록 정리하고 규칙으로 문서화 |
| 템플릿 파일에 실제 키가 들어갈 위험 | `.env`와 `.env.example`이 아직 gitignore 전이었음 | 커밋 전에 발견해 템플릿을 비우고 `.gitignore` 추가 |
| 실행하자마자 콘솔 오류 | Windows 콘솔(cp949)이 em dash(—)를 출력하지 못함. 테스트 러너는 출력 경로가 달라 이 오류를 가림 | 진입점에서 stdout을 UTF-8로 재설정, "mock 통과만으로 완료라 하지 않고 실제 실행까지 확인" 규칙 추가 |

**교훈**: 설치된 라이브러리가 import되고 메서드가 존재한다고 해서 API 형태가 맞다는 보장은 없습니다.
실제 서비스에 한 번 호출해 봐야 확인됩니다.

## 3. 하네스 설계: 에이전트가 매번 같은 기준으로 일하게

LLM 에이전트는 세션이 바뀌면 이전 판단을 기억하지 못하고, 같은 입력에도 다른 결과를 낼 수 있습니다.
그래서 "에이전트에게 맡기는 일"과 "에이전트를 둘러싼 통제 장치"를 나눠 설계했습니다.

| 구성 요소 | 역할 | 위치 |
|---|---|---|
| **작업 규칙 문서** | 처리 순서, 채점 기준, 필드별 쓰기 권한, 과거 실수와 확인 순서를 명문화 → 세션이 바뀌어도 같은 절차 | `job-judge/CLAUDE.md` |
| **세션 시작 훅** | 세션이 열리면 대기 작업(키워드 제안 대기 문항, 미분류 신규 공고)을 자동으로 확인해 에이전트에게 알림 | `job-judge/.claude/settings.json` |
| **스키마 계약** | AI 출력(JobPosting·Evaluation)을 Pydantic으로 고정. 점수는 정해진 5개 키와 항목별 상한만 허용 | `job-judge/schemas.py` |
| **LLM 미사용 구간** | 경력 요건·마감일처럼 코드로 판단 가능한 일은 규칙 엔진이 처리하고, 탈락 공고는 AI 평가로 넘기지 않음 | `job-judge/hard_filter.py` |
| **쓰기 권한 통제** | 사람이 관리하는 필드는 코드 레벨에서 AI가 쓸 수 없음. 신규 행에만 쓰는 필드와 업데이트 시 절대 안 쓰는 필드를 분리 | `job-judge/notion_writer.py` |
| **테스트** | 외부 서비스를 mock으로 격리해, 에이전트가 고친 코드가 기존 동작을 깨지 않았는지 매번 검증 | `job-judge/tests/` |

### "지침"으로 두지 않고 "코드"로 옮긴 규칙

규칙 문서에 적어 두기만 하면 에이전트가 놓칠 수 있습니다. 실제로 "필수요건 점수가 낮은데 '적극 지원'이면
경고를 붙인다"는 규칙을 문서에만 적어 뒀더니, 결과를 직접 확인해 보니 경고가 한 번도 나오지 않았습니다.
이후 이 검사를 `format_result_analysis()` 안에 코드로 옮겼습니다(`797d5e1`).
**반드시 지켜져야 하는 규칙은 문서가 아니라 코드와 테스트로 강제한다**는 원칙이 여기서 나왔습니다.

## 4. 평가 기준: 점수 선택지를 5단계로 좁히고 계산 근거 기록 (09-19)

처음 채점 기준은 배점(30/25/20/15/10)만 있고 점수를 매기는 규칙이 없어, 같은 근거에도 점수가 달라질 수
있었습니다. 외부 검토를 거쳐 하루 동안 4라운드로 고쳤습니다.

1. 근거 수준 5단계 기준표 도입 (`c62f660`)
2. 외부 검토가 코드로 재현한 버그 4개 수정 — 점수 범위 검증, 하드필터 오탈락, 남아 있던 옛 점수, 표시 안 되던 필드 (`9d746b7`)
3. 수정한 코드를 다시 실행해 보니 나온 2차 버그 3개와 "지침으로만 둔 규칙" 문제 수정 (`797d5e1`)
4. 5단계를 범위(90~100%)에서 고정값(100/75/50/25/0)으로 바꾸고, 계산 과정 기록과 반올림 규칙 명시 (`4762c64`)

외부 검토는 버전 관리·해시 기반 재현성·통계적 가중치 검증 같은 전면 재설계(v2)도 제안했지만, 혼자 쓰는
도구에는 유지 비용이 더 크다고 판단해 **채택하지 않고 검증된 버그만 고쳤습니다.** 자세한 원인·개선·결과는
[평가기준 개선 전체기록](260919_평가기준_개선_전체기록.md)에 있습니다.

## 5. 되돌린 결정: 로컬 스크립트 → 서버리스 서비스 (09-22)

신규 공고 발견 기능은 처음에 로컬 Python 스크립트로 만들었습니다(`5670cd2`). 하지만 PC가 꺼져 있으면 돌지
않고, 클라우드 예약 실행으로 옮기려면 비밀값·네트워크 허용 목록 설정 부담이 컸습니다. 그래서 이 구현을
**되돌리고**(`220bb68`) 설계를 바꿨습니다.

- **Vercel Cron**으로 PC와 무관하게 매일 실행
- 서버리스 함수는 실행 사이에 상태가 없으므로, "이미 본 공고" 상태를 로컬 JSON 대신 **MongoDB**에 저장
- 핵심 로직(목록 파싱, 신규 비교, Discord 분할 전송, Notion 기반 초기 시드)은 TypeScript로 옮기고, LLM 호출은
  여전히 없음 (`b1d7da8`)

이후 두 번째 사이트를 붙이면서 공고 타입을 사이트 무관한 형태로 일반화했고(`f0d5acd`), 한 사이트가 깨져도
다른 사이트 알림은 나가도록 사이트별로 독립 실행하게 했습니다.

## 6. 운영하면서 발견한 문제와 대응

실사용 중 드러난 문제는 고친 뒤 **같은 실수가 반복되지 않도록 규칙 문서에 원인과 확인 순서를 남겼습니다.**

| 문제 | 원인 | 대응 | 커밋 |
|---|---|---|---|
| 그룹 공채에서 두 번째 직무가 첫 직무를 덮어씀 | 계열사가 공고 URL 하나를 공유하는데 URL만으로 기존 행을 찾음 | URL + 직무명으로 매칭 | `791b5aa` |
| Discord 전송이 HTTP 400으로 실패 | 6000자 제한이 embed 하나가 아니라 **메시지 전체 합계**였음 | 필드 수·embed 수·글자 수 세 제한을 동시에 보며 채우도록 재작성 | `dc6bb13` |
| 세 등급을 한 메시지로 보내면 재현 가능한 HTTP 500 | 문서상 한도 안인데도 실패. 2개까지는 항상 성공 | 등급마다 메시지를 나눠 항상 적합→애매→부적합 순으로 전송 | `cf4e8d8` |
| 사람인 공고 본문이 비어서 옴 | 실제 본문이 같은 출처의 iframe(`view-detail`) 안에 있음 | iframe 주소로 바꿔 가져오도록 규칙화 | `7a22681` |
| 같은 회사가 두 사이트에 올라 두 번 추천됨 | 사이트마다 법인 표기가 다름 | 회사명 정규화로 중복 제거. 단, 제목에 직무·부문명이 있으면 다른 공고로 보고 유지 | `6ba492c` `5df6532` |
| 같은 공고가 표기만 달라 Notion에 중복 저장 | "A사" / "A사(B부문)"처럼 표기가 달라 URL+직무명 매칭을 피해 감 | 저장 전 회사·계열사·부문 + 직무 기준으로 먼저 확인하도록 절차 추가 | `769a259` |
| Notion 401을 몇 시간 동안 "속도 제한"으로 오판 | 오류 문구가 속도 제한처럼 보였지만, 실제로는 임시 스크립트가 `.env`를 못 찾아 키가 비어 있었음 | 증상과 확인 순서를 규칙 문서에 기록, 임시 스크립트는 `.env` 경로를 명시 | `8b634f3` |
