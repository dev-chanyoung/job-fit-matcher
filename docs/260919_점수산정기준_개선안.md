# 점수 산정 기준 개선안 (v1 → v1.1)

- 작성일: 2026-09-19
- 배경: 외부에서 받은 점수 산정 피드백 문서(`job-fit-matcher_scoring_review_and_refactoring.md`, fit-v2-draft-1)를 검토하고, Claude Code 세션과 여러 차례 의견을 주고받아 이 저장소 규모(개인용, 수동 판단 중심)에 맞는 범위로 조정한 결과.
- 반영 위치: `job-judge/CLAUDE.md`의 "4. 평가" 절에 이미 적용됨.

## 결론: 무엇을 하고, 무엇을 안 하기로 했나

외부 피드백 문서가 제안한 v2 구조(요구사항 원자화, OR/AND 그룹, 상한/하한 신뢰구간 점수, rubric 버전·해시 기반 재현성 인프라, 20~30개 표본 기반 가중치 실증 검증)는 **채택하지 않는다.** 팀 단위 채용 스크리닝 도구에 맞는 설계이고, 지금은 사용자 한 명이 가끔 JD를 붙여넣고 Claude Code가 그 자리에서 판단해주는 구조라 관리 부담이 이득보다 크다.

대신 **기존 구조(배점 5개 항목, 100점 만점, LLM이 정성적으로 판정)는 그대로 두고, "왜 이 점수인지"를 재현 가능하게 만드는 규칙만 추가**했다.

## 바뀌지 않는 것

- **배점 구조**: 필수요건_충족(0-30) / 기술스택_일치(0-25) / 업무내용_일치(0-20) / 우대사항(0-15) / 도메인_연관성(0-10). 40/30/20/10 같은 대안 가중치도 검토했지만, 데이터로 검증된 값이 아니라서 지금 바꿀 근거가 없다고 결론지었다.
- **verdict는 계속 Claude(LLM)가 정성적으로 판단**한다. 총점 임계값을 코드가 계산해서 판정을 대신 정하지 않는다 — "점수보다 정성적 판단 우선" 정책(사용자가 이미 명시적으로 요청한 방향)과 충돌하기 때문.
- **결과분석 형식**(판정 → 적합한 부분 → 부족한 부분 → 자소서 소재 → 참고 배점 순서)도 그대로 유지.

## 새로 추가한 것 (점수 산정 기준만, 버그 수정 제외)

### 1. 항목 점수를 고르는 5단계 기준표

임의로 21점, 23점처럼 숫자를 고르지 않고, 아래 중 하나를 고른 뒤 왜 그 단계인지 한 문장 근거(`profile_basis`)를 반드시 남긴다.

| 근거 수준 | 배점 대비 | 인정 기준 |
| --- | ---: | --- |
| 직접 충족 | 90~100% | JD가 요구하는 수준을 본인이 직접 수행·설명한 근거가 있음 |
| 범위 일부 부족 | 60~80% | 같은 일을 했지만 요구된 범위·복잡도·책임의 일부가 빠짐 |
| 유사 경험(전이 가능) | 40~60% | 다른 기술·환경에서 비슷한 문제를 해결했고 전이 가능한 부분과 차이를 설명 가능 |
| 기초 수준만 확인 | 15~25% | 실무 요구 수준엔 못 미치지만 수업·기초실습 등 관련 경험만 확인 |
| 확인된 미충족 / 정보 없음 | 0% | `match_level="없음"`(확인된 미충족)과 `match_level="미확인"`(정보 없음)을 반드시 구분해서 표시 |

`match_level="일부"`는 "범위 일부 부족"과 "유사 경험" 두 경우를 모두 포함하므로, 어느 쪽인지 `profile_basis`에 명시한다.

### 2. 카테고리 안에 요구사항이 여러 개일 때 합산 규칙

한 항목(예: 기술스택_일치)에 요구사항이 여러 개 걸리면 각각 %를 먼저 정하고 단순 평균해서 배점에 곱한다. JD 원문에 "핵심"/"주요"/"필수"라고 명시된 요구사항만 가중치 2배로 평균에 반영하고, 순서가 앞이거나 여러 번 언급됐다는 이유만으로 가중치를 올리지 않는다. (기존엔 이 합산 규칙 자체가 없어서 회사마다 계산 방식이 흔들릴 여지가 있었음.)

### 3. 카테고리 간 중복 채점 금지

같은 사실(예: "Java 사용 경험")을 필수요건_충족·기술스택_일치·업무내용_일치 세 항목에서 각각 좋게 평가하는 이중·삼중 채점을 금지한다. 항목마다 다른 속성만 본다:
- 기술스택_일치 → 그 기술을 아는지/써봤는지
- 업무내용_일치 → 그 기술로 실제 어떤 업무를 했는지
- 필수요건_충족 → 위 둘 중 JD가 필수로 못박은 것을 충족했는지

### 4. "조건이 아예 없음"과 "확인 못함"의 구분

JD 원문에 해당 항목 조건이 없다고 확인되면(예: 우대사항 섹션 자체가 없음) 그 항목은 만점 처리하고 "OO: 명시된 요건 없음(만점 처리)"라고 남긴다. 있는지 없는지 판단이 안 되면 0점을 주되 `evidence_quality`를 "자료 부족"으로 표시하고 "확인 필요"라고 남긴다. 이전엔 이 둘이 같은 낮은 점수로 뭉개졌다.

### 5. 점수-판정 불일치 경고

`필수요건_충족`이 배점(30) 대비 1/3 미만인데 verdict가 "적극 지원"이면, verdict 자체를 코드가 덮어쓰지는 않되 결과분석에 "⚠ 점수-판정 불일치" 경고 문장을 반드시 추가한다. verdict 계산을 통째로 코드 임계값으로 바꾸는 대신, 명백한 모순만 표시로 잡아내는 절충안.

## 이번에 다루지 않은 것 (알려진 한계)

- 점수 산정은 여전히 LLM의 정성적 판단에 크게 의존하므로, 완전히 결정론적이거나 여러 회사 간 100% 일관된 척도는 아니다. 이번 개선은 "왜 이 점수인지 설명·재현 가능"하게 만드는 데 목적이 있고, "여러 공고를 통계적으로 정밀 비교"까지 보장하지는 않는다.
- 가중치(30/25/20/15/10) 자체의 타당성은 검증하지 않았다. 실제 지원 결과가 쌓이면 재검토할 수 있으나, 소수 합격/불합격 사례로 가중치를 역산하지 않는다 (지원서 품질·경쟁률 등 다른 변수가 섞이기 때문).
- 아래는 이번 스코프에서 제외한 별도 버그 수정 항목이며, 필요시 후속 작업으로 진행한다: `Evaluation.scores`의 범위·키 검증, 하드필터의 "3년 이상" 부분문자열 오탐(신입/우대 구분 없이 탈락 처리), 필터 탈락 업데이트 시 과거 점수 컬럼이 안 지워지는 문제, `evidence_quality`/`risks`가 결과분석에 노출되지 않는 문제.
