## 1. 전체 흐름

시작 질문은 ‘CLAUDE.md에 배점은 있는데 실제 점수 산정 근거가 명확한가?’였다. ChatGPT는 점수가 코드로 산출되는 구조가 아니라 LLM이 정한 점수를 코드가 검증·합산하는 구조임을 확인했다. 이 과정에서 범위 검증 누락, 경력 필터 오판, 과거 점수 잔존 등 실제 버그도 발견했다.

처음에는 요구사항별 판정과 계산을 분리하는 큰 v2 설계가 제안됐다. 사용자가 전달한 Claude의 반론은 버그 지적에는 동의하되, 개인용 수동 도구에 비해 설계가 과하다는 것이었다. ChatGPT는 이를 수용해 기존 배점과 정성 판단을 유지하면서 버그를 고치고 짧은 채점 기준을 추가하는 방향으로 의견을 수정했다.

이후 사용자가 커밋·푸시한 코드를 반복 검토하면서, 문서의 규칙과 실제 구현 사이 차이를 확인했다. 경력 필터 예외와 불일치 경고를 보완하고, 마지막에는 충족률 고정값·계산 근거·반올림 지침이 CLAUDE.md에 반영된 것을 확인했다.

| 순서 | 단계 | 핵심 질문·쟁점 | 결과 |
| --- | --- | --- | --- |
| 1 | 최초 v1 검토 | 배점만 있고 산정 근거가 없는가? | 실제 평가 구조와 코드 결함 확인 |
| 2 | fit-v2-draft-1 제안 | 근거를 고정하고 가중치를 어떻게 정할까? | 요구사항 기반 계산·새 4개 영역·정보 부족 처리 제안 |
| 3 | Claude 반론 | 개인용 도구에 과한 설계 아닌가? | 대규모 재설계보다 가벼운 수정 권고 |
| 4 | ChatGPT 의견 조정 | 무엇만 남기면 실용적인가? | 버그 수정 + 짧은 채점 기준 + 근거 표시 |
| 5 | v1.1 개선안 검토 | 5단계 구간과 평균 규칙이면 충분한가? | 구간·중복·N/A 만점 정책의 한계 지적 |

| 7 | bb0e162 검토 | 재발견한 필터·경고 문제 해결 여부 | 9개 직접 확인 항목 통과 |
| 8 | 후속 CLAUDE.md 확인 | 최종 채점 명확화 반영 여부 | 고정값·score_breakdown·마지막 반올림 지침 확인 |

이 과정은 공식 릴리스가 v1→v2로 일괄 전환됐다는 뜻이 아니다. `fit-v2-draft-1`은 제안서 이름이고, `v1.1`은 사용자가 전달한 개선안 문서의 명칭이다. 그 이후 단계는 커밋 또는 확인된 지침 변경으로 구분한다.

## 2. 출발점: 사용자의 문제의식과 운영 목적

사용자는 본인의 경험·프로젝트·기술을 채용공고와 대조해 지원할 가치가 있는지 판단하고, 근거를 Notion에 정리하는 개인용 도구를 만들고 있었다. 대규모 자동 채용 심사보다는 사용자가 JD 링크나 텍스트를 건네면 Claude가 분석하는 흐름이 중심이었다.

초기 요청은 다음과 같았다.

- 점수를 판별하는 실제 로직을 찾을 것.
- CLAUDE.md에 적힌 기준이 구현과 일치하는지 확인할 것.
- 점수가 명확한 근거로 산정되는지 판단할 것.
- 필요한 수정과 가중치 근거를 Markdown으로 정리할 것.

대화 중 계속 유지된 운영 원칙은 ‘점수보다 정성적 판단을 우선한다’는 것이었다. 점수는 지원 판단의 보조 정보이며 합격확률로 제시하지 않는다.

처음에는 저장소 접근이 막혔으나, 사용자가 GitHub를 연결하고 접근 권한을 제공한 뒤 실제 파일을 읽어 검토를 진행했다.

## 3. 최초 v1 검토: 어떤 구조였나

검토 기준 커밋: `c5e94db34c0f3fc010050e8e8f42827e3d8bc027`.

### 3.1 실제 실행 경로

| 경로 | 평가 기준·담당 | 코드의 역할 |
| --- | --- | --- |
| 기본 Claude Code 수동 경로 | CLAUDE.md와 profile.md를 읽은 Claude가 평가 JSON 작성 | judge_manual.py가 로드·검증·저장 |
| API 경로 | evaluate_prompt.txt를 받은 모델이 평가 JSON 반환 | evaluator.py가 호출·파싱·검증 |
| 공통 저장 | 이미 작성된 항목 점수 사용 | notion_writer.py가 합산·출력·저장 |
| 사전 필터 | hard_filter.py | 경력 요건과 마감 여부 검사 |

핵심 발견은 ‘evaluator.py라는 파일이 있어도 기본 사용 경로에서 코드가 점수를 계산하는 것은 아니다’라는 점이었다. 기본 경로는 evaluator.py를 건너뛴다. API도 모델에게 항목 점수를 받아오는 방식이었다.

### 3.2 당시 배점

| 항목 | 배점 |
| --- | ---: |
| 필수요건 충족 | 30 |
| 기술스택 일치 | 25 |
| 업무내용 일치 | 20 |
| 우대사항 | 15 |
| 도메인 연관성 | 10 |
| 합계 | 100 |

배점과 ‘근거 없으면 0점’ 원칙은 있었지만, 직접 경험과 유사 경험의 점수 차이, 복수 조건의 합산, N/A 처리, 판정 기준이 충분히 정해져 있지 않았다.

ChatGPT의 당시 판단은 ‘정성 검토용으로는 유용하지만 회사 간 숫자 차이를 그대로 신뢰할 수준은 아니다’였다.

| F04 | 근거 없는 평가도 허용, 요구사항별 연결을 강제하지 않음 | 검증 범위의 한계 |

직접 재현된 예시는 필수요건 100점·음수·빈 점수·오타 키의 검증 통과, ‘5년 이상’의 필터 통과, ‘신입 또는 경력 3년 이상’의 탈락 등이었다. 실제 Notion에 쓰지 않고 mock 요청을 확인해 점수 속성 누락도 확인했다.

## 4. 첫 번째 큰 제안: fit-v2-draft-1

사용자는 ‘배점을 논하기 전에 항목별 점수의 근거를 고정하는 것이 우선인가?’라고 물었고, ChatGPT는 그렇다고 답했다. 이어 피드백·채점 기준·가중치·리팩토링 명세를 하나의 문서로 작성했다.

문서명: `job-fit-matcher_scoring_review_and_refactoring.md`.

### 4.1 제안한 구조

- 지원자격을 점수와 별도 게이트로 분리.
- JD 요구사항을 작은 단위로 나누고 근거와 연결.
- 모델은 충족 수준을 판단하고 Python이 수치 변환·합산·판정.
- 요구사항 ID, 원문 출처, 근거 ID, 중복 제거 키 및 대체조건 그룹 관리.
- 미확인과 미충족, 해당 없음을 구분.
- 미확인이 있으면 점수 하한·상한과 확인 범위를 제시.
- rubric·프로필·JD·모델·프롬프트 버전과 해시 보존.
- 수동/API 공통 계산기를 도입하고 대표 공고로 검증.

하한·상한은 미확인 항목을 모두 미충족 또는 충족으로 놓은 경우의 범위였다. 통계적 신뢰구간이나 합격확률이 아니었다. 이후 반론에서 ‘신뢰구간 점수’라고 요약되기도 했지만, 정확한 의미는 위와 같다.

### 4.2 제안 가중치와 그 한계

| 새 영역 | 상대 중요도 | 정규화한 배점 |
| --- | ---: | ---: |
| 업무 수행 경험 | 8 | 40 |
| 기술 적합성 | 6 | 30 |
| 개발 품질·운영 역량 | 4 | 20 |
| 추가 우대역량 | 2 | 10 |

계산은 `100 × 상대 중요도 / 20`이었다. 지원자격은 별도 처리하고 업무·기술 중심으로 평가하려는 설계였다.

그러나 상대 중요도 8·6·4·2 자체는 ChatGPT의 설계 판단이었다. 통계적으로 학습하거나 실제 합격 데이터로 검증한 최적값은 아니었다. ChatGPT는 뒤에 이 한계를 다시 강조하며 지금 배점을 바꿀 근거가 충분하지 않다고 의견을 수정했다.

### 4.3 함께 제안된 계산·판정 정책

- 충족도: 직접 1.0 / 일부 부족 0.75 / 전이 가능 0.5 / 기초 0.25 / 미충족 0 / 미확인 null.
- 영역 안에서는 중요도 가중평균.
- N/A만 분모에서 제외하고 적용 배점으로 환산.
- 미확인에는 범위와 coverage를 표시하며 coverage 100%일 때만 확정 점수 저장.
- 적극 지원·지원 고려의 초기 기준으로 80·60점 등을 제안하되 필수조건과 정보량도 별도 확인.
- 20~30개 대표 공고를 사람이 먼저 판단하고 가중치 후보와 비교.

이 정책들은 당시의 제안이다. 뒤의 경량안에 모두 채택된 것이 아니다.

## 5. Claude의 반론: 결함 진단에는 동의, 설계 규모에는 반대

사용자가 전달한 Claude의 피드백은 먼저 F01·F03·F06·F07·F08의 코드 상태를 확인하고, 근거 없는 비판이 아니라 실제 문제를 짚은 검토라고 평가했다.

다만 해결책에 대해서는 다음과 같이 반론을 제기했다.

| 쟁점 | 사용자가 전달한 Claude 의견 |
| --- | --- |
| 시스템 규모 | 한 사람이 가끔 JD를 입력하는 개인용 도구에 v2 구조는 과함 |
| 요구사항 모델링 | 원자화·OR/AND 그룹·canonical_key 관리 부담이 큼 |
| 정보 부족 처리 | coverage 100%에서만 점수를 쓰면 많은 공고의 점수 컬럼이 비게 될 수 있음 |
| 재현성 인프라 | rubric·source/profile hash까지 지금 도입할 필요는 낮음 |
| 평가 목적 | 정성 판단 우선 정책인데 점수 정밀도 개선에 지나치게 집중함 |
| 검증 규모 | 표본 기반 검증 프로그램은 실제 불편 사례가 쌓인 뒤 고려 |

Claude가 권한 즉시 수정 범위는 다음이었다.

1. Pydantic으로 scores 키·범위 검증.
2. 경력 숫자와 정규식으로 필터 개선, 신입 대체경로 구분.
3. 필수요건 점수와 총점 임계값으로 코드가 verdict 결정.
4. 필터 탈락 업데이트에 점수 null 명시.
5. evidence_quality·risks 출력.

중요한 점은 이 시점의 Claude 피드백에 ‘verdict 코드화’가 있었다는 것이다. 이후 전달된 v1.1 문서에서는 LLM 정성 판정을 유지하는 방향으로 바뀌었다. 두 시점의 의견을 같은 것으로 합치지 않는다.

또한 우대조건이 원래 없는 N/A와 수집 실패 UNKNOWN은 최초 v2에서도 구별하려던 개념이었다. N/A 자체가 반드시 coverage를 떨어뜨리는 것은 아니었다. 다만 모델링·수집 부담과 점수 공란의 운영상 우려는 유효한 반론으로 받아들여졌다.

## 6. ChatGPT의 재검토와 방향 전환

ChatGPT는 개인용 워크플로 대비 v2가 크다는 비판을 수용했다. 이후 권고를 ‘명백한 버그 패치 + 짧은 채점 기준표 + 판정 근거·불확실성 표시’로 줄였다.

### 6.1 수용한 의견

- 작은 코드 검증으로 해결할 수 있는 결함부터 고친다.
- 새로운 파일·엔진·해시 체계 도입을 당장 필수로 삼지 않는다.
- 정성 판단 우선 정책을 유지한다.
- 기존 30/25/20/15/10 배점은 유지한다.
- 실제 점수가 이상한 사례가 쌓이면 필요한 부분만 추가한다.

### 6.2 그대로 수용하지 않은 의견

**verdict를 점수 임계값으로 무조건 바꾸는 것에는 동의하지 않았다.**

LLM이 판정하는 것 자체는 오류가 아니다. 점수 산정이 아직 모호한 상태에서 임계값만 고정하면 모호함을 코드로 확정하는 결과가 된다. 필수 자격 하나의 미충족이 다른 점수에 묻힐 수도 있다.

대안은 정성 판정을 유지하되 명백한 불일치·필수조건 미충족·자료 부족을 표시하는 것이었다.

**‘신입’이라는 단어가 있으면 무조건 통과시키는 방식에도 주의를 제기했다.**

신입 또는 경력이라는 실제 대체경로인지, 신입 지원 불가라는 배제인지, 통합 공고의 다른 직무 설명인지 구분해야 한다고 설명했다.

**버그 수정만으로 채점 근거 문제까지 해결되지는 않는다고 보았다.**

기존 배점을 유지하더라도 직접·부분·유사·기초·미충족의 짧은 기준표가 필요하다고 제안했다. 복잡한 계산 엔진보다 이 기준과 설명을 우선했다.

## 8. v1.1에 대한 ChatGPT의 두 번째 피드백

전체 방향은 적절하다고 평가했지만, 다음 다섯 가지를 보완 대상으로 남겼다.

### 8.1 범위형 비율은 임의 선택을 남긴다

직접 충족이 90~100%이면 같은 근거로도 27~30점 중 하나를 골라야 한다. 일부 부족과 유사 경험의 구간도 60%에서 겹친다.

따라서 100/75/50/25/0% 고정값을 권고했다. 수업·실습만 있어도 JD가 ‘기초 이해’를 요구한다면 직접 충족으로 볼 수 있어야 한다는 설명도 제안했다. 경험의 이름보다 JD 목표 수준에 상대적으로 평가해야 한다는 뜻이다.

### 8.2 계산 과정이 남아야 재현할 수 있다

가중평균 규칙 자체는 큰 개선이다. 여기에 요구사항별 비율·중요도·계산식을 한 줄로 남기고 마지막에 한 번만 반올림하자고 권했다.

예시:

```text
Java 100%×2, Spring 75%×2, Redis 25%×1
→ (200+150+25)/5 = 75%
→ 25×0.75 = 18.75
→ 19점
```

### 8.3 중복 금지와 항목 정의가 충돌한다

‘Java 사용’을 기술스택에서 평가하면서, 필수요건에서도 ‘필수 Java를 충족하는가’를 평가하면 같은 근거가 두 항목에 들어간다.

ChatGPT는 기존 배점을 유지한다면 제한적 중복을 정책으로 인정하되 같은 카테고리의 반복 채점과 이름만 바꾼 중복을 금지하자고 제안했다. 완전한 중복 제거를 하려면 영역을 재설계해야 한다. 이 제안이 최종 지침에 반영됐다고 확인되지는 않았다.

### 8.4 N/A 만점은 공고 간 비교에 영향을 준다

조건이 없는 공고에 자동 만점을 주면 상세 조건을 많이 적은 공고보다 점수가 유리해질 수 있다. 대안으로 N/A를 분모에서 빼고 적용 배점에 대해 환산하자고 제안했다.

그러나 이후 확인한 운영 지침은 계속 ‘조건 없음 → 만점 + 설명’을 유지했다. 이 제안은 채택된 것으로 기록하지 않는다. 뒤의 대화에서는 유지된 정책의 의미와 한계를 설명했다.

### 8.5 낮은 필수요건 총점만으로 모든 모순을 잡지 못한다

필수조건 대부분을 충족해 점수는 높아도 결정적인 자격 하나가 부족할 수 있다. 따라서 ‘10점 미만 경고’는 보조 검사이며 모든 필수 지원자격 검증을 대신하지 못한다고 설명했다.

## 12. API 프롬프트 동기화 논의

사용자는 API용 평가 프롬프트에도 개선이 반영됐는지 반복 확인했다.

직접 읽은 당시 `prompts/evaluate_prompt.txt`에는 기존 배점, 추측 금지, 근거 없으면 0점, 유사 경험 구분만 있었다. 새 5단계 비율·가중평균·N/A 정책·중복 규칙은 없었다.

ChatGPT는 두 가지를 구분했다.

- 점수 검증·경고·저장처럼 공통 Python 코드의 개선은 API 경로에도 적용된다.
- 모델에게 전달되는 세부 채점 기준은 별도 프롬프트이므로 CLAUDE.md 수정만으로 동기화되지 않는다.

## 13. 후속 CLAUDE.md: 핵심 채점 기준 반영

사용자가 다시 CLAUDE.md를 보라고 요청했고, 다음 세 가지가 반영된 것을 확인했다.

### 13.1 고정 충족률

| 수준 | 최종 확인한 지침의 비율 |
| --- | ---: |
| 직접 충족 | 100% |
| 범위 일부 부족 | 75% |
| 전이 가능한 유사 경험 | 50% |
| 기초 수준만 확인 | 25% |
| 확인된 미충족 또는 정보 없음 | 0% |

`match_level="일부"`는 75%와 50%를 모두 포함하므로 profile_basis에 어느 유형인지 명시한다. 미확인과 없음은 같은 0%라도 라벨을 구분한다.

### 13.2 계산 근거 기록

요구사항이 2개 이상인 카테고리는 `Evaluation.score_breakdown[카테고리명]`에 비율·가중치·계산 결과를 한 줄로 남기도록 지시한다. 하나뿐인 경우 생략할 수 있다고 되어 있다.

### 13.3 마지막 단계에서 반올림

가중평균과 중간값은 소수를 유지하고 배점을 곱한 카테고리 최종값에서 한 번만 반올림한다.

ChatGPT는 핵심 세 가지가 문서상 반영됐다고 판단했다. 추가로 정확히 .5일 때의 반올림 방식까지 정하면 Python 기본 round와의 차이를 줄일 수 있다고 제안했다.

이 후속 읽기에서 확인한 CLAUDE.md blob SHA는 `29a9ebbdb3a1856f83840f72f0eb95d3c6ece227`이었다. 이는 파일 식별값이지 전체 커밋 SHA가 아니다. 당시 전체 저장소의 해당 커밋은 따로 확정하지 않았다.

### 13.4 추가로 확인한 운영 변경

- 직무와 무관한 법정·신분상 우대조건을 역량 점수에서 제외한다는 지침 추가.
- 그러한 조건만 있고 직무 관련 우대가 없으면 N/A 만점 처리 유지.
- Notion 표의 결과분석은 한 줄 요약으로 바꾸고 상세 근거는 페이지 본문에 작성하도록 변경.
- 본문에 적합·부족·위험·자소서 소재·배점·계산 근거를 남기도록 지시.

이 단계의 검토는 CLAUDE.md 읽기였다. score_breakdown의 실제 스키마·저장·본문 출력까지 실행 검증한 것으로 확대 해석하지 않는다. 본문 작성은 문서상 별도 작업이므로 누락 시 상세 근거가 표시되지 않을 위험도 문서에 명시돼 있었다.

## 14. 기술스택·우대사항 처리에 관한 마지막 정리

사용자는 우대사항이 없으면 만점을 주고 설명을 덧붙이는지, 기술과 우대조건이 없거나 부족할 때 각각 어떻게 되는지 확인했다.

| 상황 | 마지막 확인 지침의 처리 | 의미 |
| --- | --- | --- |
| 공고 전체 확인 결과 관련 조건 없음 | 기술 25점 또는 우대 15점 만점 | 해당 없음으로 받은 점수 |
| 조건 유무 자체를 확인하지 못함 | 해당 항목 0점 + 자료 부족 | 정보 수집 부족 |
| 조건은 있으나 프로필에 경험 정보 없음 | 해당 요구사항 0% + 미확인 | 경험 부재로 단정하지 않음 |
| 실제 미경험·미충족 확인 | 해당 요구사항 0% + 없음 | 확인된 부족 |
| 관련 경험 일부 보유 | 25/50/75% 중 해당 수준 | 인정한 범위와 부족 이유 기록 |
| 요구 수준 직접 충족 | 해당 요구사항 100% | 직접 근거 기록 |

‘우대사항’ 또는 ‘기술스택’이라는 제목이 없는 것과 조건 자체가 없는 것은 다르다. 본문·담당업무·자격요건에 관련 조건이 있으면 평가한다. 회사가 사용할 것 같은 기술을 추측해 조건으로 추가하지 않는다.

우대조건 하나가 부족하다고 우대 카테고리 전체를 0점으로 만드는 것이 아니다. 요구사항별 충족률을 가중평균한다. 우대 미충족은 그 자체로 필수 지원자격 미충족이 아니다.

N/A 만점은 운영상 선택된 정책이다. ChatGPT가 제시했던 재정규화 대안으로 바뀐 것은 아니다. 결과에는 ‘명시된 요건 없음으로 만점’이라는 설명을 남겨야 하며, 그 문구의 자동 생성·누락 검증까지 확인된 것은 아니다.

## 16. ChatGPT 판단에서 정정·보완된 부분

### 16.1 ‘코드로 전부 고정’이 유일한 답은 아니었다

처음에는 점수의 재현성을 높이는 설계에 비중을 크게 두었다. 사용자 운영 방식과 정성 판단 우선 정책을 고려한 뒤, 설명 가능성을 높이는 최소한의 규칙으로 범위를 조정했다.

### 16.2 계산한 가중치와 검증된 가중치를 구분했다

40/30/20/10은 상대 중요도를 정규화한 결과이지만, 상대 중요도 자체는 주관적 설계값이었다. 계산식이 있다고 객관적 최적값이 되는 것은 아니다. 이후 기존 배점 유지에 동의했다.

### 16.3 LLM verdict 자체를 결함으로 보는 시각을 수정했다

문제는 LLM이 판단한다는 사실보다 근거·필수조건·점수와의 모순을 놓치는 것이다. 최종 방향은 정성 판정 유지와 코드 경고의 병행이었다.

### 16.4 문서 검토와 코드 검토의 결론을 분리했다

첨부 v1.1 문서에 버그가 별도 작업으로 남아 있어 미해결로 설명한 뒤, 사용자가 최신 코드를 보라고 요청했다. 실제 저장소를 읽고 해결된 항목을 정정했다. 이후에도 ‘문서 반영’과 ‘실행 검증’을 나누어 기록했다.

### 16.5 ‘현재’라는 표현은 확인 시점에 종속된다

API 프롬프트, CLAUDE.md, Python 파일이 서로 다른 시점에 읽혔다. 따라서 최신 문서 변경만으로 API 및 저장 코드까지 반영됐다고 결론 내리지 않았다. 이 이력 문서도 2026-09-26 현재 코드 상태를 새로 보증하지 않는다.

## 17. 검증 근거와 남은 한계

| 범위 | 실제 확보한 근거 | 주장할 수 없는 것 |
| --- | --- | --- |
| 최초 결함 | 파일 읽기와 잘못된 점수·필터 입력 직접 실행 | 모든 공고에서 오류가 난다는 주장 |
| 점수 null 갱신 | mock 요청 payload 확인 | 실제 Notion 데이터 정리 완료 |
| 11a2b9f | 스키마·출력 검토와 핵심 함수 재현 | 전체 pytest 통과를 직접 확인했다는 주장 |
| bb0e162 | 6개 필터 + 3개 경고 사례 실행 | 자유문 모든 표현의 완벽한 처리 |
| 후속 CLAUDE.md | 고정 충족률·계산 근거·반올림 문구 확인 | 새 스키마·저장·API 동기화의 실행 검증 |
| 점수의 타당성 | 명시된 규칙과 근거 추적 방법 | 합격확률·통계적으로 검증된 가중치 |

마지막까지 남은 논점은 다음과 같다.

- JD 해석과 충족 수준 선택에는 LLM 판단이 남는다.
- N/A 만점은 공고 간 점수 비교에 영향을 준다.
- 미확인과 미충족은 같은 0%이므로 설명을 같이 봐야 한다.
- 필수요건과 기술스택의 완전한 중복 제거는 이루어졌다고 보기 어렵다.
- 낮은 필수요건 점수 경고가 모든 필수자격 미충족을 탐지하지는 않는다.
- API 세부 지침 동기화는 마지막 확인 이후 상태가 미확인이다.
- 정확한 .5 반올림 방식과 계산 내역 검산 여부는 추가 확인 대상이다.
- 상세 분석을 별도로 본문에 쓰는 운영에서는 저장 완료와 근거 표시 완료가 다를 수 있다.

## 18. 이 과정에서 도출한 설계 원칙

1. 배점 조정보다 같은 근거를 어떻게 평가할지 먼저 정한다.
2. 객관성이라는 말을 점수 형식 검증, 계산 재현성, 판단 타당성으로 나누어 설명한다.
3. 개인용 도구에서는 필요한 만큼만 구조화하고 실제 오류부터 고친다.
4. 문서의 지시와 코드가 보장하는 조건을 구분한다.
5. 숫자의 모순은 코드로 검사하되 정성 판단을 무조건 총점으로 대체하지 않는다.
6. 조건 없음·미확인·미충족을 서로 다른 의미로 표시한다.
7. 채택하지 않은 제안도 이유와 함께 남긴다.
8. 버그 수정 뒤에는 원래 실패한 구체적인 사례를 다시 실행한다.
9. 모델 판단이 남는 시스템을 완전 결정론적 평가나 합격예측 모델이라고 부르지 않는다.

이 대화의 결과는 큰 v2를 일괄 구현한 것이 아니라, 초기 v1의 불명확성을 확인하고 두 모델의 의견을 비교해 개인용 규모에 맞는 개선을 단계적으로 선택한 과정이었다. 마지막에 확인한 핵심 변화는 기존 배점과 정성 판정을 유지하면서 고정 충족률, 계산 근거, 반올림 지침, 점수 검증, 필터 보완, 경고·위험 표시를 추가한 것이다.
