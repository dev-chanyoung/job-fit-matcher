## 배경: 이 작업이 왜 시작됐나

job-judge는 사용자가 채용공고 JD를 붙여넣으면 Claude Code 세션이 직접 정규화·평가하고, 하드필터/Notion 저장만 코드(`judge_manual.py`)에 맡기는 개인용 지원적합도 분석 도구다. v1 채점 기준은 "필수요건_충족(0-30) / 기술스택_일치(0-25) / 업무내용_일치(0-20) / 우대사항(0-15) / 도메인_연관성(0-10)"이라는 배점 구조만 있었고, **점수를 매기는 구체적인 규칙이 없었다** — 같은 근거를 보고도 21점을 줄지 23점을 줄지는 순전히 그때그때의 판단이었다.

사용자가 이 문제를 외부에 검토를 요청해 받아온 피드백 문서(`job-fit-matcher_scoring_review_and_refactoring.md`, 제안 버전명 `fit-v2-draft-1`)가 시작점이었다. 이 문서는 코드를 직접 실행해서 v1의 실제 결함 10가지(F01~F10)를 확인했고, 이를 해결하기 위한 **v2 전체 재설계**(요구사항 원자화, OR/AND 그룹, 상한/하한 신뢰구간 점수, rubric 버전·해시 기반 재현성 인프라, 20~30개 표본 기반 가중치 실증 검증)를 제안했다.

## 0차: v2 전체 도입 여부 판단 — "이건 이 도구 규모에 안 맞는다"

**원인 진단**: v2가 제안한 구조는 팀 단위 채용 스크리닝 시스템에 맞는 설계였다. 이 프로젝트는 사용자 한 명이 가끔 JD를 붙여넣고 Claude Code가 그 자리에서 판단해주는 워크플로이므로, rubric 버전 관리·해시 기반 재현성 보장·통계적 가중치 검증 같은 인프라는 얻는 이득보다 유지 관리 부담이 더 크다고 판단했다.

**개선 방향 확정**: v2 구조는 채택하지 않고, 실제로 검증된 버그만 가볍게 고치는 쪽으로 방향을 잡았다. 배점 구조(30/25/20/15/10)도 "40/30/20/10이 더 낫다"는 v2의 제안 대신 그대로 유지하기로 했다 — 두 값 모두 데이터로 검증된 게 아니라 설계자가 정한 값이라서, 굳이 바꿀 근거가 없었기 때문이다.

이 판단 이후 4차례에 걸쳐 "가볍게, 필요한 만큼만" 원칙 아래 실제 개선이 진행됐다.

## 1차 개선 (커밋 `c62f660`): 채점 기준을 재현 가능하게 만들기

### 원인
"필수요건_충족 23점"이라는 결과만 있고, 그 23점이 어떤 근거에서 나왔는지 재구성할 방법이 없었다. 회사마다 다른 사람(혹은 다른 세션의 Claude)이 채점해도 일관된 결과가 나오려면, 최소한 "이 근거는 몇 %짜리인지" 판단하는 공통 기준이 필요했다.

### 개선안
1. **배점 대비 % 기준표**: 직접 충족/범위 일부 부족/유사 경험/기초만 확인/미충족·정보없음 5단계로 나누고, 각 단계마다 근거 문장을 profile_basis에 남기도록 함 (이 시점엔 90~100%처럼 범위로 정의).
2. **카테고리 내 여러 요구사항 합산 규칙**: 한 항목에 요구사항이 여러 개면 단순평균해서 배점에 곱하도록 명시 (이전엔 이 규칙 자체가 없어서 계산 방식이 흔들렸음).
3. **카테고리 간 중복 채점 금지**: 같은 사실(예: "Java 경험")을 여러 항목에서 반복 채점하지 않도록 각 항목이 보는 속성을 분리.
4. **조건 없음(N/A) vs 확인 못함 구분**: JD에 조건이 아예 없으면 만점, 판단이 안 되면 0점+"확인 필요" 표시로 분리.
5. **점수-판정 불일치 경고 (문서 지침으로만)**: 필수요건 점수가 낮은데 verdict가 "적극 지원"이면 결과분석에 경고를 넣으라고 CLAUDE.md에 지침으로만 추가.

### 결과
`CLAUDE.md`의 "4. 평가" 절에 반영. 이 시점엔 문서(지침) 변경만 있었고 코드는 건드리지 않았다 — 이어지는 라운드에서 "지침으로만 적어둔 규칙이 실제로 지켜지는지"가 다시 문제가 된다 (5번 항목, 3차 개선에서 재발견).

## 3차 개선 (커밋 `797d5e1`): "고쳤다"고 한 것을 재검증했더니 나온 2차 버그

외부 피드백이 **2차 개선 이후의 최신 코드를 다시 실제로 실행해서** 재검증한 결과, 2차 개선에서 만든 `extract_mandatory_min_years()` 로직 자체가 너무 단순해서 생긴 새로운 버그 3개와, 1차 개선에서 "지침으로만" 추가했던 규칙이 실제로는 안 지켜지는 문제 1개를 추가로 발견했다.

### 원인과 개선

1. **최소 연차 0년도 탈락시킴**: "경력 0~3년"/"경력 0년 이상"처럼 사실상 "누구나 지원 가능"인 조건도 무조건 탈락 처리하고 있었다. → 연차 매칭 결과가 0이면 애초에 "필수 연차 요건"으로 세지 않도록 수정 (`if years > 0`).
2. **"신입"이라는 글자만 있으면 무조건 대체경로로 오판**: "경력 3년 이상 (신입 지원 불가)"처럼 신입을 명시적으로 배제하는 문장도 "신입"이 들어있다는 이유만으로 통과시켰다. → "신입" 근처(10자 이내)에 "불가/제외/안됨/어려움" 같은 부정어가 있으면 대체경로로 인정하지 않는 정규식(`_NEW_GRAD_NEGATION_RE`) 추가.
3. **"우대"가 문장 어디에 있든 전체를 우대로 착각**: "경력 3년 이상, 금융권 경험 우대"에서 "우대"는 금융권 경험에만 붙은 건데, 문장 전체에 "우대"가 있으면 "3년 이상" 요건까지 전부 우대로 취급해 통과시켰다. → 쉼표/슬래시로 나뉜 절(clause) 단위로만 "우대" 여부를 판단하도록 수정 (`_clause_containing()`).
4. **점수-판정 불일치 경고가 실제로 안 뜸**: 1차 개선에서 CLAUDE.md에 "필수요건 점수가 낮은데 적극 지원이면 경고를 넣어라"고 적었지만, 이건 Claude가 Evaluation JSON을 쓸 때 기억해서 챙겨야 하는 지침일 뿐이었고 코드에는 검사 로직이 없었다. → `notion_writer.format_result_analysis()`가 `필수요건_충족 < 배점(30)/3`이고 `verdict == "적극 지원"`이면 경고 줄을 자동으로 추가하도록 코드에 직접 구현. 판정 자체는 여전히 코드가 덮어쓰지 않는다.

### 결과
4가지 모두 재현 스크립트로 버그를 먼저 재현 확인 → 수정 → 같은 스크립트로 다시 돌려서 정상화 확인. pytest 102개 전체 통과.

## 4차 개선 (커밋 `4762c64`): 남은 모호함 마감 + API 경로 동기화

1~3차를 거치고도 여전히 남아있던 채점 기준의 모호함 3가지를 마무리하고, API 경로(`evaluator.py`)에는 새 기준이 전혀 반영 안 되어 있던 문제도 이 라운드에서 같이 해결했다.

1. **% 범위 → 고정값**: "직접 충족 90~100%"처럼 범위를 쓰면 같은 근거를 보고도 매번 다른 숫자를 고를 수 있어 재현성이 완전히 닫히지 않았다. → 100/75/50/25/0 다섯 개 고정값만 쓰도록 변경.
2. **항목별 계산 내역 미기록**: 카테고리 안에 요구사항이 여러 개일 때 가중평균 규칙(1차 개선)은 있었지만, 그 계산 자체를 어디에도 남기지 않아서 나중에 "왜 19점인지" 재구성할 수 없었다. → `Evaluation.score_breakdown: dict[str, str]` 선택 필드를 추가(스키마가 알 수 없는 카테고리 키는 거절)해서 `"Java 100%x2, Spring 75%x2, Redis 25%x1 -> 75% -> 18.75/25 -> 19점"` 형식으로 한 줄 기록하게 하고, `format_result_analysis()`가 이걸 "(참고) 배점" 아래에 그대로 노출하도록 연결.
3. **반올림 규칙 부재**: 항목별로 각각 반올림한 뒤 더하는지, 최종값만 반올림하는지가 안 정해져 있어서 계산 순서에 따라 결과가 미묘하게 달라질 수 있었다. → "카테고리 % 가중평균은 소수 그대로 유지하고, '% × 배점' 최종값 하나만 반올림한다"고 명시.
4. **API 경로 미동기화**: 기본 경로(Claude Code 세션, CLAUDE.md)는 새 기준을 다 반영했지만, `evaluator.py`가 읽는 `prompts/evaluate_prompt.txt`에는 5단계 % 기준, 가중평균 규칙, 중복채점 금지, N/A 구분, score_breakdown 필드 중 아무것도 없었다 — API로 실행하면 완전히 다른 기준으로 채점될 수 있는 상태였다. → `evaluate_prompt.txt`를 CLAUDE.md와 동일한 내용으로 재작성.

### 결과
`schemas.py`/`notion_writer.py`/`CLAUDE.md`/`prompts/evaluate_prompt.txt` 동시 수정, pytest 107개 전체 통과, `format_result_analysis()` 직접 실행으로 `score_breakdown` 줄 렌더링 확인.

## 최종 결과물: 2026-09-19 기준 평가 기준 전체 스펙

### 처리 순서 (변경 없음)
1. URL/텍스트로 JD 입력받기 → 2. `JobPosting` JSON으로 정규화 → 3. **하드필터** (LLM 미사용, 코드로만 판정) → 4. **평가** (통과한 경우만, LLM이 `Evaluation` JSON 작성) → 5. `judge_manual.py`로 하드필터 재확인 후 Notion 저장.

### 하드필터 (`hard_filter.py`)
탈락 사유는 두 가지뿐이다.
- **경력 요건 미충족** (`extract_mandatory_min_years()`): 아래 어느 하나에 해당하면 통과, 나머지는 최소 연차만큼 탈락.
  - 신입 대체경로가 있음 (`"신입 또는 경력 3년 이상"`) — 단, "신입" 근처에 "불가/제외/안됨/어려움" 같은 부정어가 있으면 대체경로로 인정 안 함.
  - 해당 연차 언급이 속한 절(comma/slash로 구분)에 "우대"가 있고 "필수"가 없음 — 다른 절의 "우대"는 영향 없음.
  - 최소 연차가 0년 — 사실상 경력무관이므로 탈락 사유 아님.
  - 그 외 애매한 문구는 자동 탈락시키지 않음 (정규식이 인식하는 패턴이 아니면 통과).
- **마감 지남** (`is_past()`).
- (`education_requirement`의 "졸업자만 지원 가능"류 문구는 지원자가 이미 졸업했으므로 탈락 사유 아님 — 2026-09-19 사용자 확인.)

### 배점 구조 (변경 없음, `schemas.SCORE_CAPS`)
필수요건_충족(0-30) / 기술스택_일치(0-25) / 업무내용_일치(0-20) / 우대사항(0-15) / 도메인_연관성(0-10) = 총 100점. `Evaluation.scores`는 정확히 이 5개 키만 허용하고 각 값은 0~해당 상한 범위여야 한다 (벗어나면 검증 실패).

### 항목 점수 산정 기준
| 근거 수준 | 배점 대비 | 인정 기준 |
|---|---:|---|
| 직접 충족 | 100% | JD가 요구하는 수준을 본인이 직접 수행·설명한 근거가 있음 |
| 범위 일부 부족 | 75% | 같은 일을 했지만 요구된 범위·복잡도·책임의 일부가 빠짐 |
| 유사 경험(전이 가능) | 50% | 다른 기술·환경에서 비슷한 문제를 해결했고 전이 가능한 부분과 차이를 설명 가능 |
| 기초 수준만 확인 | 25% | 실무 요구 수준엔 못 미치지만 수업·기초실습 등 관련 경험만 확인 |
| 확인된 미충족 / 정보 없음 | 0% | `match_level="없음"`(확인된 미충족)과 `match_level="미확인"`(정보 없음)을 반드시 구분 |

- 한 카테고리에 요구사항이 여러 개면 각각 %를 정한 뒤 가중평균(원문에 "핵심"/"주요"/"필수"로 명시된 것만 가중치 2배)해서 배점에 곱한다.
- 요구사항 2개 이상인 카테고리는 이 계산을 `Evaluation.score_breakdown[카테고리명]`에 한 줄로 기록한다 (예: `"Java 100%x2, Spring 75%x2, Redis 25%x1 -> 75% -> 18.75/25 -> 19점"`).
- 반올림은 "% × 배점"의 최종값에서 한 번만 한다.
- 같은 사실(예: "Java 사용 경험")을 여러 카테고리에서 중복 채점하지 않는다 — 카테고리마다 다른 속성만 본다.
- JD에 해당 조건이 아예 없다고 확인되면 그 카테고리는 만점 처리, 판단이 안 되면 0점+"확인 필요"로 구분한다.

### 판정 (verdict)
"적극 지원"/"지원 고려"/"보류" 중 하나를 LLM이 정성적으로 판단해서 정한다 (코드가 임계값으로 대신 정하지 않음). 단, `필수요건_충족 < 10`(배점 30의 1/3 미만)인데 verdict가 "적극 지원"이면 `notion_writer.format_result_analysis()`가 코드로 "⚠ 점수-판정 불일치" 경고를 자동으로 붙인다 (판정 자체는 덮어쓰지 않음).

### 결과분석 출력 순서 (`format_result_analysis()`)
판정 → (불일치 시) ⚠ 경고 → 정보 충분도 → 적합한 부분 → 부족하거나 안 맞는 부분 → (있으면) 위험 요인 → 자소서 소재 → (참고) 배점 + score_breakdown 계산 근거.

### 저장 경로
`judge_manual.py`(Claude Code 세션이 직접 정규화·평가, 기본 경로)와 `judge.py`(API 경로, `evaluator.py` + `prompts/evaluate_prompt.txt`) 둘 다 같은 `schemas.py`/`notion_writer.py`를 거치므로 스키마 검증·점수-판정 경고·Notion 쓰기 권한 규칙은 두 경로에 동일하게 적용된다. 프롬프트 텍스트(채점 기준 설명)도 4차 개선에서 두 경로를 동일하게 맞췄다.

## 알려진 한계 (의도적으로 남겨둔 것)

- **완전한 결정론적 재현은 아니다.** 점수 산정은 여전히 LLM의 정성적 판단에 크게 의존한다. 이번 4차례 개선은 "같은 근거면 같은 계산 규칙을 거치게" 만드는 데 목적이 있었지, LLM이 매번 정확히 같은 %를 고른다고 보장하지는 않는다.
- **`evidence`가 비어 있어도 평가 자체는 통과된다.** 근거 없는 평가를 막는 검증은 아직 추가하지 않았다.
- **가중치(30/25/20/15/10) 자체의 타당성은 검증하지 않았다.** 데이터 기반 검증 없이 그대로 유지하기로 한 결정이며, 실제 지원 결과가 쌓이면 재검토할 수 있다.
- **v2가 제안했던 큰 구조(요구사항 원자화, OR/AND 그룹, 신뢰구간 점수, rubric 버전·해시 관리, 실증적 가중치 검증)는 여전히 채택하지 않았다.** 지금 규모에서 관리 부담이 이득보다 크다는 판단은 유효하다.
