# 채용공고 지원적합도 분석 도구 — 개발 청사진 (Vibe Coding용)

> 이 문서는 AI 코딩 어시스턴트에게 그대로 넘겨 "이 스펙대로 구현해줘"라고 요청할 수 있는 실행 스펙입니다.

## 0. 한 줄 요약
사용자가 채용공고 링크 또는 JD 텍스트를 넣으면, 미리 등록된 내 프로필과 대조하여 **서류 경쟁력 점수 + 근거표 + 지원 추천**을 JSON으로 뽑아 콘솔에 출력하고 Notion DB에 저장하는 CLI 도구.

## 1. 기술 스택 (고정)
- 언어: Python 3.11+
- LLM: Anthropic API (`anthropic` 패키지)
- 본문 추출: `trafilatura`
- HTTP: `httpx`
- CLI: `typer`
- Notion 연동: `notion-client`
- 환경변수: `python-dotenv`
- 설정 파일: `.env` (`ANTHROPIC_API_KEY`, `NOTION_API_KEY`, `NOTION_DB_ID`)

```
pip install anthropic trafilatura httpx typer notion-client python-dotenv
```

## 2. 프로젝트 구조
```
job-judge/

├── profile.md                # 사용자 프로필 (수동 작성)
```

## 3. 데이터 스키마 (Pydantic, `schemas.py`)

```python
from pydantic import BaseModel
from typing import Literal, Optional

class JobPosting(BaseModel):
    company: str
    position: str
    source_url: Optional[str] = None
    fetched_at: str  # ISO timestamp
    employment_type: Optional[str] = None       # 신입/경력/인턴 등
    required_years: Optional[str] = None
    education_requirement: Optional[str] = None
    location: Optional[str] = None
    must_have: list[str] = []
    nice_to_have: list[str] = []
    tech_stack: list[str] = []
    responsibilities: list[str] = []
    deadline: Optional[str] = None
    missing_fields: list[str] = []              # 본문에서 못 찾은 항목

class Evidence(BaseModel):
    jd_requirement: str
    profile_basis: str
    match_level: Literal["강함", "일부", "미확인", "없음"]

class Evaluation(BaseModel):
    verdict: Literal["적극 지원", "지원 고려", "보류"]
    scores: dict[str, int]      # 필수요건_충족(0-30), 기술스택_일치(0-25),
                                  # 업무내용_일치(0-20), 우대사항(0-15), 도메인_연관성(0-10)
    evidence: list[Evidence]
    gaps: list[str]
    cover_letter_topics: list[str]
    risks: list[str]
    evidence_quality: Literal["근거 충분", "일부 부족", "자료 부족"]
```

## 5. 하드 필터 규칙 (`hard_filter.py`, 코드로만 처리 — LLM 사용 금지)
```python
def hard_filter(job: JobPosting) -> tuple[bool, list[str]]:
    reasons = []
    if job.required_years and "3년" in job.required_years:
        reasons.append("경력 3년 이상 요구")
    if job.deadline and is_past(job.deadline):
        reasons.append("마감 지남")
    if job.education_requirement and "졸업자" in job.education_requirement:
        # 졸업예정자 처리 규칙은 여기서 명시적으로 분기
        pass
    return (len(reasons) == 0, reasons)
```
- 규칙은 하드코딩된 조건문으로만 작성. LLM 판단에 맡기지 않는다.
- 필터 통과 여부와 사유를 항상 함께 반환해 evaluator 단계 이전에 로그로 남긴다.

## 6. 프롬프트 (전문 — `prompts/` 파일로 저장)

### 6-1. `normalize_prompt.txt`
```
당신은 채용공고 텍스트를 정해진 JSON 스키마로 변환하는 파서입니다.

[규칙]
- 본문에 명시되지 않은 정보는 추측하지 말고 null 또는 빈 배열로 둔다.
- 확인하지 못한 항목은 missing_fields 배열에 필드명을 적는다.
- 필수요건(must_have)과 우대사항(nice_to_have)을 반드시 분리한다.
- 출력은 JSON만. 설명 문장, 마크다운 코드블록 금지.

[출력 스키마]
{JobPosting 스키마 그대로 삽입}

[채용공고 원문]
{jd_text}
```

### 6-2. `evaluate_prompt.txt`
```
당신은 채용 서류 검토를 돕는 평가자입니다. "합격 확률"은 절대 계산하지 마세요 —
경쟁률과 내부 기준을 알 수 없으므로 이는 근거 없는 추측입니다.
대신 "서류 경쟁력"을 평가하세요.

[규칙]
- 프로필이나 JD에 없는 내용은 추측하지 말 것.
- 근거를 제시할 수 없는 점수는 0점으로 처리할 것.
- 유사 경험을 요구사항과 동일한 경험으로 취급하지 말 것 (match_level을 "일부"로 구분).
- evidence는 JD 요구사항 하나당 최소 1개 작성.

[출력 스키마]
{Evaluation 스키마 그대로 삽입}

[정규화된 JD]
{normalized_jd_json}

[내 프로필]
{profile_md_content}
```

## 7. `judge.py` CLI 흐름 (의사코드)
```python
@app.command()
def run(input: str):
    # 1. 입력 판별: URL이면 extractor로 본문 추출 시도
    if input.startswith("http"):
        text = extractor.fetch(input)
        if text is None:
            typer.echo("본문 추출 실패 — JD 텍스트를 직접 붙여넣어 주세요.")
            raise typer.Exit()
        source_url = input
    else:
        text = input  # 또는 파일 경로에서 읽기
        source_url = None

    # 2. 정규화
    job = normalizer.normalize(text, source_url)

    # 3. 하드 필터
    passed, reasons = hard_filter.hard_filter(job)
    if not passed:
        typer.echo(f"필터 탈락: {reasons}")
        notion_writer.save(job, evaluation=None, filtered_reason=reasons)
        raise typer.Exit()

    # 4. 평가
    profile_text = open("profile.md").read()
    evaluation = evaluator.evaluate(job, profile_text)

    # 5. 출력 + 저장
    print_result(job, evaluation)
    notion_writer.save(job, evaluation)
```

## 8. Notion DB 연동 (기존 트래커 `백엔드_공고_트래커` 재사용)

새 컬럼을 만들지 않고, 이미 운영 중인 트래커에 최대한 얹어 쓴다. 필드를 세 그룹으로 나눠 자동화의 쓰기 권한을 명확히 구분한다.

### 기존 스키마 (실제 DB, 변경 없음)
| 필드 | 타입 | 옵션 |
|---|---|---|
| 회사명 | title | |
| 직무명 | text | |
| 공고링크 | url | |
| 지원상태 | select | 관심있음/지원완료/지원안함 |
| 마감일 | date | |
| 기업규모 | select | 스타트업/중견기업/대기업 |
| 도메인 | select | 커머스/핀테크/금융/제조자동차/IT서비스/통신 |
| 기술스택 | multi_select | Java/Spring Boot/MySQL/AWS/Kotlin/Spring/Kafka/Docker/Python/TypeScript/React/Azure/Kubernetes/Go/C#/C++/MFC (고정 옵션, 자동화가 새 옵션을 만들지 않음) |
| 연차요건 | select | 신입~3년/경력무관 |
| 우선순위 | select | 상/중 |
| 지원동기메모 | text | |
| 결과분석 | text | |

### 유일한 추가 컬럼
| 필드 | 타입 | 설명 |
|---|---|---|
| 평가기준버전 | text | 프롬프트가 바뀔 때마다 버전 문자열(`v1`, `v2` ...)을 남겨 나중에 판단이 달라진 이유 추적 |

### 필드별 쓰기 권한 (`notion_writer.py`가 반드시 지킬 규칙)
| 그룹 | 필드 | 자동화 동작 |
|---|---|---|
| **자동 채움** | 회사명, 직무명, 공고링크, 마감일 | JD 정규화 결과(`JobPosting`)를 그대로 매핑 |
| | 기술스택 | LLM이 뽑은 `tech_stack`을 기존 옵션 목록과 대조해 **일치하는 것만** 선택. 목록에 없는 기술명은 컬럼에 넣지 않고 `결과분석` 텍스트에만 언급 |
| | 연차요건 | "신입~3년" / "경력무관" 둘 중 하나로만 강제 분류. 애매하면 "신입~3년"으로 보수적으로 처리 |
| **제안(사람이 최종 확인)** | 결과분석 | `Evaluation` 전체(판정/점수/근거요약/부족한점/자소서소재/리스크)를 정리된 텍스트 블록으로 이 필드 하나에 기록. 새 컬럼(판정/총점 등)을 만들지 않는다 |
| | 기업규모, 도메인 | 확신이 낮으면 값을 넣지 말고 `결과분석`에 "추정: OO"로만 남김. 최종 확정은 사람이 함 |
| **자동화 금지(사람 영역)** | 지원상태, 우선순위, 지원동기메모 | 기존 행이면 절대 덮어쓰지 않음. 새 행 생성 시에도 빈 값으로 둠 |

`결과분석` 필드에 들어갈 텍스트 포맷 예시:
```
[v1 평가결과 / 2026-09-16]
판정: 지원 고려
점수: 필수요건28 기술스택18 업무내용15 우대사항10 도메인5 (총76)
근거: Spring Boot 백엔드 개발 경험 강함 매치 / Kafka 실운영 경험 미확인
부족한 점: 메시지 브로커 운영 경험 없음
자소서 소재: 실시간 처리 프로젝트 경험
추정 기업규모: 중견기업 (근거: 채용공고에 명시 없음, 직원 수 추정)
```

### 중복 방지 (필수)
- 새 행을 만들기 전에 반드시 `공고링크`로 기존 행을 조회한다.
- 기존 행이 있으면 새로 만들지 않고 **자동 채움 필드 + 결과분석만 업데이트**한다(지원상태/우선순위/지원동기메모는 건드리지 않음).
- 기존 행이 없을 때만 새 페이지를 생성한다.

## 9. 구현 순서 (커밋 단위 태스크)
1. [ ] `schemas.py` 작성 + 단위 테스트(빈 값/필수값 검증)
2. [ ] `profile.md` 실제 내용 채우기
3. [ ] `normalizer.py`: 프롬프트 로드 → LLM 호출 → JSON 파싱 → `JobPosting` 검증. 샘플 JD 3개로 수동 확인
4. [ ] `hard_filter.py`: 규칙 3~4개 작성 + 유닛테스트(통과/탈락 케이스 각각)
5. [ ] `evaluator.py`: 프롬프트 로드 → LLM 호출 → `Evaluation` 검증. 같은 JD로 2회 실행해 점수 일관성 확인
6. [ ] `extractor.py`: trafilatura로 URL 3개(성공/실패 케이스 포함) 테스트, 실패 시 None 반환 확인
7. [ ] `notion_writer.py`: 공고링크로 기존 행 조회(중복 확인) → 없으면 생성/있으면 업데이트, 기술스택 옵션 매칭 로직, 결과분석 텍스트 포맷 함수. 신규 저장 1건 + 업데이트 1건 테스트
8. [ ] `judge.py`: 전체 파이프라인 연결, `python judge.py <URL 또는 텍스트파일>` 로 end-to-end 실행
9. [ ] 완료 기준: 실제 공고 5개를 넣어 전 과정이 에러 없이 돌고, Notion에 5행이 정상 저장됨
